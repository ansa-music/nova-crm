Это рабочий файл контекста. Claude Code читает его автоматически при запуске в этой папке — сюда вынесено всё, что нужно знать, чтобы продолжать работу без повторных объяснений.

## Что это за проект

Nova CRM — production SaaS-платформа, полностью написанная с помощью Claude. Модель: один **Owner** (сам Nurba) + независимые **менеджеры** (в интерфейсе — «Технар»), каждый работает в своей изолированной персональной странице, которая теперь в UI называется **«стол»** (desk), а не «лист». Явно НЕ модель отделов/бухгалтеров — столы это личные рабочие пространства менеджеров, Owner видит сводку над всеми.

## Терминология (важно!)

Внутренний код (типы, роли, коллекции Firestore) **не переименован** — это чисто UI/копирайтинг-слой:

- `Role = "owner" | "admin" | "manager" | "viewer"` — как было. Но `ROLE_LABELS.manager === "Технар"` (`src/types/role.ts`) — везде в интерфейсе роль `manager` подписана как «Технар».
- «Страница» (`WorkspacePage`, коллекция `pages`) в интерфейсе называется **«стол»** (desk). В коде переменные/типы всё ещё `page`/`WorkspacePage`, но роуты, сервисы и часть текстов используют слово «desk»/«стол» (`DesksPage.tsx`, `deskCoverService.ts`, `requestDeskView`, `/desks`).
- «Дашборд» и «Столы» — теперь **разные экраны** (раньше дашборд был единственной точкой входа): `/dashboard` (графики, рейтинг, KPI), `/desks` (грид обложек всех доступных столов), `/people` (список участников — раньше жил в сайдбаре), `/page/:pageId` (сам стол — открытая таблица). `HomePage` (`/`) — умная точка входа: если у тебя есть свой ответственный стол, сразу открывает его; иначе — дашборд-лендинг.

## Стек

React 19, TypeScript, Vite 6, Tailwind, shadcn/ui, Framer Motion, **GSAP + @gsap/react** (тонкие stagger-анимации на десктопе, специально отключены на телефонах/touch — см. «Cut dashboard GSAP stagger enter on phones and touch»), Zustand, Firebase (Auth + Firestore — durable источник истины), **Supabase** (Postgres + Storage + Realtime — см. отдельный раздел ниже), TanStack Virtual (виртуализация таблицы), dnd-kit (drag&drop), sonner (тосты), canvas-confetti.

## ⚠️ Storage больше не отключён — есть загрузка файлов через Supabase

Старое правило «Storage намеренно отключён, никаких загрузок файлов нигде в проекте» **больше не действует**. Firebase Storage по-прежнему не используется (нет Blaze-плана), но появился **Supabase Storage** как отдельный сервис:

- `src/lib/supabase.ts` — клиент Supabase (anon key прямо в коде, как и Firebase web API key — это нормально, доступ гейтится Storage policies на бакете).
- Бакет `row-files` (`ROW_FILES_BUCKET`), путь `{workspaceId}/{pageId}/{rowId}/{id}_{filename}` для вложений строк и `{workspaceId}/covers/{pageId}/{uuid}.ext` для обложек стола.
- **Вложения к строке** (`rowAttachmentService.ts`, тип `RowAttachment` в `src/types/page.ts`) — до 10 МБ, только `jpeg/png/webp/gif/avif/pdf`. Доступны и в ячейке таблицы, и в `RowCardSheet`.
- **Обложка стола** (`deskCoverService.ts`) — фото для карточки на `/desks`, до 10 МБ, только `jpeg/png/webp`.
- Есть и отдельный тип столбца **«Ссылка» (`url`)** — «Диск URL»-подход (ручная ссылка на файл вместо аплоада) тоже остался как альтернатива, где Supabase-аплоад избыточен.

## Supabase-мост для строк таблицы (обязательно прочитать перед правкой DataTable/rowService)

Firestore остаётся **источником истины** (durable copy), но каждая строка таблицы **зеркалируется** в Postgres-таблицу `row_records` через `src/services/rowRecordsService.ts`. Причина: бесплатный план Firebase («Spark») ограничивает число одновременных live-listener'ов, и это душило realtime на дашборде/вторичных экранах (см. коммиты «Cut dashboard Spark listeners», «Cut remaining Spark live listeners; poll secondary screens»). Supabase Realtime (`postgres_changes`) взял на себя часть live-подписок.

Правила, которые нельзя нарушать:
- Запись в Firestore — как и раньше, через `pageService`/`subPageService`. Зеркалирование в Supabase — **best-effort, никогда не бросает исключение** (`mirrorUpsertRow`, `mirrorPatchRowCells`, `mirrorReorderRows`, `mirrorDeleteRow*` — все ловят свои ошибки и молча игнорируют).
- Supabase **никогда не может удалить/создать строку в Firestore** — `mergeFirestoreAndSupabaseRows()` явно использует Firestore как источник самого факта существования строки (`sbMap`, но набор строк — от Firestore), Supabase только подмешивает более свежие `cells`/`attachments`/`order`, если они новее по `updatedAt` (с запасом ~250–500мс на рассинхрон часов).
- Если правишь что-то в row CRUD (`pageService.ts`, `subPageService.ts`) — почти наверняка нужно продублировать вызов в `rowRecordsService.ts` (`mirrorUpsertRow`/`mirrorPatchRowCells(Bulk)`/`mirrorReorderRows`/`mirrorDeleteRow(ForPage|ForSubPage)`), иначе Supabase-копия тихо расходится с Firestore.

## Статус-варианты (`statusOptions`) — обновлённая модель, не как раньше

Раньше (см. старую версию этого файла) все три option-типа — Статус, Ответственный, кастомные поля — одинаково НЕ хранили список в колонке, всё жило на `Workspace`. Промежуточная версия этого файла утверждала, что это изменилось для «Статус» (`getColumnOptions()` якобы предпочитает `column.statusOptions`) — **это устарело/неверно, откатили обратно**: `getColumnOptions()` (`src/utils/columnOptions.ts`) для типа `status` **всегда** читает `workspace.statusOptions` (с фоллбэком на `DEFAULT_STATUS_OPTIONS`), `column.statusOptions` для этого типа сейчас не читается нигде (само поле помечено как «DEAD for type status» в `src/types/page.ts`) — статус, как и Ответственный с кастомными полями, полностью workspace-wide. `DataTable.tsx`'s `displayColumns` перезаписывает `.statusOptions` каждой колонки результатом `getColumnOptions()`, поэтому Канбан и дропдаун таблицы всегда видят один и тот же список.

- Firestore rules (`columnStatusOptionsPreserved()` в `firestore.rules`) разрешают Технару/ответственному менять остальные поля столбца (label/width/order), но **список `workspace.statusOptions`** менять может только Owner — не-owner-редактор получит `permission-denied`, если попробует.
- `ensureDoneStatus()`/`isDoneStatusLabel()`/`findDoneStatusOption()` — гарантируют, что в любом резолвленном списке статусов всегда есть что-то похожее на «Готово» (проверка по подстроке: «готов», «done», «успеш», «закрыт»), даже если Owner его случайно удалил из списка — иначе конфетти/рейтинг/группировка «Готово» сломались бы молча. `isDoneStatusLabel()` явно исключает метки со отдельным словом «не» («Не готово», «Ещё не готово») — раньше такая метка тоже засчитывалась как «готово» по чистой подстроке, из-за чего фильтр «Не готово», подсчёт `notDone`, конфетти и `markRowDone()` (свайп/кнопка «Готово», Ctrl+D) могли молча сработать неправильно на статусе-отрицании.
- Ответственный и кастомные поля Owner-а — **по-прежнему** чисто workspace-wide, тут ничего не изменилось.

## Новое в правах доступа (`firestore.rules`)

- `canAccessPage()` теперь дополнительно пускает **ответственного за стол** (`isResponsiblePage`), даже если его uid не в `allowedUsers` — раньше ответственность без явного `allowedUsers` не давала доступа.
- Собственный документ участника (`members/{uid}`) всегда читаем самим этим пользователем, даже когда документ ещё не существует — иначе `get()` на отсутствующий `members/{uid}` кидал `permission-denied` и приложение тостовало «Нет доступа к части данных» на пустом месте.
- **Скрытые столы + запрос на просмотр** — новая подсистема (`viewRequestService.ts`, коллекция `viewRequests`): если стол скрыт (`hiddenByResponsible`) и у тебя нет доступа, можно отправить `requestDeskView()` — уходит уведомление ответственному, после `resolveDeskViewRequest({status:"approved"})` тебе выдаётся `allowedUsers`-доступ через `toggleUserPageAccess`. UI — отдельный лист «Скрытые столы» с состояниями pending/approved прямо на карточке.
- CI деплоит `firestore:rules` вместе с hosting на каждый пуш в `main` (см. `.github/workflows/deploy.yml`: `firebase deploy --only hosting,firestore:rules`) — отдельный `npm run deploy:rules` для прод-деплоя **больше не обязателен вручную**, он уже часть автодеплоя. Полезен только для локальной проверки правил до пуша.

## Критические уроки и подводные камни (НЕ повторять)

- **`e.key` vs `e.code`** — `e.key` зависит от раскладки клавиатуры. На русской раскладке физическая клавиша Z печатает «я», а не «z». Любые проверки горячих клавиш (Ctrl+Z/C/V и т.п.) должны идти через `e.code` (`"KeyZ"`, `"KeyC"`...), никогда через `e.key`, иначе сочетания клавиш тихо не работают на русской раскладке.
- **`serverTimestamp()`** нельзя использовать на полях, которые форматируются для отображения (`updatedAt`/`createdAt`, которые потом показываются пользователю) — вызывает краши при рендере. Использовать `Date.now()`.
- Firestore `delete`-правила никогда не должны проверять `request.resource.data` — это поле не существует при удалении.
- Firestore list-запросы (`collection().where(...)`) требуют однородных прав на все документы в результате — иначе весь запрос падает с `permission-denied`, даже если у пользователя есть доступ к части документов. Личное пространство (`personalZones/{uid}/reports`) поэтому вынесено в изолированную коллекцию по uid, а не смешано в общий список.
- Квоты на количество страниц у менеджера — только через atomic Firestore batch writes, не читай-потом-пиши (race condition).
- **`activeRole`** (режим симуляции роли Owner/Admin) — чисто клиентское поле для UI, Firestore rules никогда не должны ему доверять для реальных решений о доступе.
- `allowedUsers` (просмотр) и `editableUsers` (редактирование) — разные права, не путать. `responsibleUserId` даёт админ-права в рамках конкретной страницы и теперь ещё и доступ на чтение даже без `allowedUsers` (см. `isResponsiblePage`), но не доступ на уровне всего workspace.
- «Статус», «Ответственный» и кастомные поля — **больше не идентичны** (см. раздел выше): у Статуса появился per-column список с Owner-only правом менять уже существующий, у остальных двух список всё ещё чисто workspace-wide. Не переноси автоматически логику с одного типа на все три без проверки.
- Undo/redo — **глобальный** стек (`src/utils/undoStore.ts`), не привязан к компоненту таблицы: переживает навигацию между страницами. Ctrl+Z обрабатывается ОДНИМ слушателем на уровне приложения (`GlobalUndoHotkeys.tsx` в `AppLayout`), не дублировать в `DataTable.tsx`.
- **Классический баг, который уже чинили дважды**: любая проверка вида `column.type === "status"` для решения «можно ли начинать текстовое редактирование этой ячейки» — неполная. Нужно проверять `isOptionColumn(column.type)` (покрывает status + responsible + custom), иначе двойной клик по ячейке «Ответственный»/кастомного поля тихо включает фантомное текстовое редактирование, которое блокирует ВСЕ горячие клавиши на странице до перезагрузки.
- Лид-стол уведомлений о новых сообщениях — при подписке на Firestore `conversations` массив вначале приходит пустым (до первого снапшота), затем реальными данными. Верный паттерн — база «видел ли я именно ЭТУ переписку», а не «это первый вызов эффекта вообще».
- **iOS Safari / Google OAuth**: `authDomain` должен быть `firebaseapp.com`, а не кастомный хостинг-домен (`web.app`) — на `web.app` был `redirect_uri_mismatch` на iPhone. Google-логин на мобильном идёт через `signInWithRedirect`, не `signInWithPopup`; `getRedirectResult()` не должен блокировать/ложно показывать «окно закрыто» для обычного email+password входа, и не должен реагировать на преждевременный `null` от Auth (иначе denied Firestore read разлогинивает живую сессию).
- **Firebase Spark listener limits**: не вешай новые постоянные `onSnapshot`-подписки бездумно на второстепенные экраны (дашборд-виджеты, вторичные вкладки) — упрёшься в лимиты бесплатного плана. Для строк таблицы уже есть Supabase Realtime мост (`rowRecordsService.ts`) — используй его паттерн, а не добавляй ещё один Firestore listener.
- Отдельный standalone HTML-проект «Living Archive CRM», который всплывал раньше — архитектурно несовместим с Nova CRM, не пытаться сливать.

## Модель прав (кратко)

Roles: `owner` > `admin` > `manager` (label «Технар») > `viewer`. Только Owner проходит `isOwner()` в правилах безусловно на любой странице. `canEditPage(page) = owner || responsibleUserId == uid || (canAccessPage && uid in editableUsers)`. `canAccessPage(page) = owner || isResponsiblePage || uid in allowedUsers`. История изменений (`/history`) — читает только Owner.

## Известные ограничения (осознанные, не баги)

- Рейтинг (`leaderboard`) обновляется только когда сам ответственный человек открывает свой дашборд — нет backend-функций, которые обновляли бы его за него. Если человек долго не заходил — его цифры устареют. Раздельно был исправлен баг, из-за которого сумма «Готово» скрытого стола не попадала в рейтинг — теперь попадает.
- Undo/redo — только для действий в текущей сессии/вкладке браузера текущего пользователя, не восстанавливает чужие действия и не переживает `F5`.
- Личное пространство (`personalZones/{uid}/reports`) — отдельная, полностью изолированная от общих статусов/списков подсистема с собственными жёстко заданными статусами; НЕ путать с общей системой Статус/Ответственный/кастомных полей.
- Supabase-зеркало (`row_records`) — best-effort кэш/канал реального времени, не резервная копия и не источник истины: при расхождении Firestore всегда выигрывает по факту существования строки, Supabase — только по свежести содержимого.

## Дальнейшие идеи, которые обсуждались, но НЕ реализованы

Сохранённые виды (комбинации фильтр+группировка+сортировка), автоматизация «если → то» (уведомления по правилам), импорт из amoCRM/Excel, Telegram-бот, вычисляемые столбцы (формулы), публичная форма захвата лида, клиентский портал, кастомные роли, оффлайн-режим (PWA), свайп-действия на мобильном для произвольных полей (для статуса уже сделано, для остального — сознательно нет, риск конфликта с горизонтальным скроллом широкой таблицы на touch).

## Сборка «Table v2» (сентябрь 2026) — что появилось, чтобы не переделывать заново

Подробный список — в `CHANGELOG.md`. Ключевые архитектурные моменты:

- **`confirmDialog()` / `promptDialog()`** (`src/utils/appDialog.ts`) — единственный способ
  спросить подтверждение или строку у пользователя. `window.confirm`/`window.prompt` в
  проекте больше не используются; хост `AppDialogHost` смонтирован в `AppLayout`.
  Использование: `if (!(await confirmDialog({ title, description, destructive: true }))) return;`
- **Числа хранятся канонически** (`src/utils/numberInput.ts`, `normalizeNumericInput`):
  при коммите/вставке в number/currency ячейку строка нормализуется («1 500,50» → «1500.5»).
  `parseLooseNumber` — единый парсер для итогов, группировок, канбана.
- **Итоги столбцов** (`src/utils/columnAggregates.ts`) — выбор вида итога per view хранится в
  `localStorage` (`nova-crm:column-aggregates:<viewKey>`). Ничего не пишется в Firestore.
- **Фильтр столбца ключуется по RAW-значению ячейки** (`filters[colKey]: Set<rawValue>`),
  а показывает подпись (`FilterValueEntry { value, label, count, color }`). Не возвращать
  сравнение по label — это и был старый баг для статус-колонок.
- **Поиск** сравнивает и raw, и `cellDisplayText()` (подпись статуса / формат даты).
- **Клавиатура**: `openRequest` (DataTable → TableRow → TableCell) — счётчик, по которому
  активная picker-ячейка открывает Radix Select (через синтетический keydown Enter, поэтому
  глобальный обработчик игнорирует `!e.isTrusted`) или календарь. Space открывает карточку.
  Пока открыта карточка строки (`expandedRowId`), обработчик клавиш таблицы полностью молчит.
- **RowCardSheet редактируемая** — `onCellChange` = `handleStatusChange` (persist + undo + конфетти).
- Tailwind: добавлен breakpoint `xs: 420px`.

  `fillPreview` (только для отрисовки) → `applyFill` пишет все ячейки и кладёт ОДНУ команду
