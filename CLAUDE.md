## Кто владелец и как общаться

Владелец — Nurba, общается **по-русски**. Решения (архитектурные и дизайнерские) принимай

Формулировки часто неформальные/с опечатками — ориентируйся на суть. Nurba нередко ведёт
**несколько сессий Claude Code параллельно** над одним `main` — перед крупной задачей делай
`git fetch`/смотри последние коммиты в `main`, не доверяй локально закэшированному состоянию.

## Что это за проект

Nova CRM — production SaaS, написанная с помощью Claude. Один **Owner** (Nurba) + независимые
**менеджеры** (в UI — «Технарь»), каждый работает на своей изолированной персональной странице,
в UI называемой **«стол»** (desk). НЕ модель отделов/бухгалтеров — столы это личные рабочие
пространства менеджеров, Owner видит сводку над всеми.

## Терминология

Внутренний код (типы, роли, коллекции Firestore) не переименован — это чисто UI-слой:

- `Role = "owner" | "teamlead" | "admin" | "manager" | "os" | "viewer"`, но `ROLE_LABELS.manager === "Технарь"`
  (`src/types/role.ts`) — везде в UI роль `manager` подписана «Технарь».
- Роль **`teamlead` («Тимлид»)** — ведёт людей: участники, заявки, роли, доступы к столам
  (allowedUsers/editableUsers/ответственный), настройки workspace, объявления
  (`hasFullAccess()` в `utils/permissions.ts` и в `firestore.rules`). **Таблиц столов не видит
  вообще**: `canAccessPage`/`canEditPage`/`canUsePersonalZone` в правилах исключают
  `isTeamLead`, на клиенте `isBlockedFromDesks` + `canOpenDesk`; «Столы» скрыты (дашборд виден, но без личного
  блока), `/` ведёт на «Пользователи». Только Owner: удаление workspace, бэкап, история, любые записи об
  Owner. `hasFullDeskAccess` на клиенте = только Owner.
- **Вторая роль** (`members.extraRoles`, только `manager`/`os` — `EXTRA_ROLES` в `types/role.ts`):
  Owner + Технарь, Тимлид + Технарь, Тимлид + ОС. Права складываются: `usePermissions().roles`/
  `hasRole()`, `rolesOf()`/`memberHasRole()` для участников. Люди/настройки решает только основная
  `role`; вторая роль открывает столы (Технарь), Грок (Технарь у ОС) и оценки (ОС). Тимлид видит
  таблицы только с «+ Технарь» (`deskBlocked` / `isDeskBlockedFor` на клиенте, `isDeskBlocked()` в
  правилах). **Тимлид + Технарь видит ЧУЖИЕ столы на ЧТЕНИЕ без запроса просмотра**
  (`isTeamLeadTech()` в правилах, `seesAllDesks()` в `utils/permissions.ts` и проп
  `seesAllDesks` у `canOpenDesk`/`fetchPageIfAccessible`): он и людей ведёт, и сам работает за
  столом. Правка так НЕ даётся — `canEditPage` по-прежнему требует ответственного или явный
  `editableUsers`, и личная зона чужого стола закрыта (`canUsePersonalZone` не тронут).
  Клаузa не зависит от документа, поэтому нефильтрованный list столов ему тоже проходит.
  Проверено эмулятором — 12 проверок (`leadtech.mjs`): читает строки и вкладки чужого стола,
  не правит и не создаёт, в личную зону не лезет; Тимлид без Технаря, Тимлид + ОС и чужой
  технарь по-прежнему получают отказ. Проверки «это ОС/Технарь/Тимлид» пиши через роли, не через `role ===`. Тимлид
  **не меняет себе** роль, вторую роль, ник ОС и не удаляет себя (правила members + замок в
  «Пользователи»); это делает Owner или другой Тимлид.
- Роль **`os` («ОС»)** — без своего стола: не создаёт столы, не управляет чужими, `/` ведёт
  на «Технари», в меню скрыты «Столы» и «Грок лимит» (коллекции Grok закрыты и в
  правилах, `canUseGrok`). Owner может симулировать её через
  RoleSwitcher — теперь **только Owner** (списки в `allowedSimulatedRoles` и в правиле
  `activeRole` синхронны).
- «Страница» (`WorkspacePage`, коллекция `pages`) в UI — **«стол»** (desk). Код/типы остаются
  `page`/`WorkspacePage`, но роуты/сервисы часто используют «desk»/«стол» (`DesksPage.tsx`,
  `deskCoverService.ts`, `/desks`).
- Экраны: `/dashboard` (единый дашборд, см. ниже), `/desks` (грид обложек столов), `/people`
  (участники), `/page/:pageId` (сам стол). `HomePage` (`/`) — если есть свой ответственный
  стол, сразу открывает его, иначе дашборд-лендинг.
- **«Столы»** (`DesksPage.tsx`): скрытые столы (`hiddenByResponsible`) стоят в общей сетке с меткой
  «Скрыт» (+ чип «Скрытые»), войти можно только с доступом — отдельного листа «Скрытые столы» нет.
- **«Доступ ко всем»** (кнопка ТОЛЬКО у Owner в шапке «Столов», `AllDesksAccessButton`,
  `setAllDesksVisibility`): тот же переключатель, что у каждого стола («открыт для всех /
  скрыт», `togglePageVisibility`), разом на все АКТИВНЫЕ столы (неактуальные и столы ОС не
  трогаются). «Открыть все на просмотр» — `allowedUsers` = все активные участники +
  ответственный, `hiddenByResponsible: false`; `editableUsers` НЕ трогаем — правка не выдаётся и
  не отнимается. «Закрыть все» — `allowedUsers` = только ответственный, `hidden: true`; выданные
  просмотры снимаются, смотреть — по «Запросить просмотр». Пришли новые люди — нажать «Открыть
  все» ещё раз (доступ лежит списком на столе, общего флага нет). Счётчик «открыто всем /
  закрыто / частично» — по настоящему списку, а не по флагу «скрыт»: правила смотрят только
  `allowedUsers`, и стол с флагом «открыт», но без людей в списке, на деле закрыт.
- **«Неактуальные столы»** вместо удаления: `page.inactive`/`inactiveAt`/`inactiveBy`, ставят и снимают
  только Owner и Тимлид (`canRetireDesks`, `setPageInactive`, ⋯ на обложке и меню стола). В правилах
  это поля Тимлида, ответственному их трогать нельзя; жёсткое удаление стола — только Owner.
  `useWorkspace().pages` — только активные столы (дашборд, «Технари», месячные вкладки, квота
  Технаря их не видят), `inactivePages` — лист «Неактуальные», `allPages` — всё (открыть стол по
  ссылке). Уход в неактуальные снимает claim Технаря на этот стол (может завести новый), возврат
  ставит claim, если он свободен.
- **Месячные вкладки** (`monthTabService.ts`, хук `useMonthTabAutopilot` в `AppLayout`): у
  каждого стола Технаря одна вкладка на месяц по Алматы. В новом месяце вкладка создаётся
  (id `month-YYYY-MM`) или подхватывается существующая «Сентябрь 2026»/«сентябрь» и один раз
  делается вкладкой по умолчанию; на странице пишутся `autoMonthKey`/`autoMonthSubPageId`.
  Сессия Owner обслуживает все столы Технарей, сессия Технаря — свой. Старые вкладки не
  трогаются, заказы Технарь переносит сам. Кто «работает за столом» — один помощник
  `worksAsTechnician()` (`utils/peopleDesks.ts`): роль Технаря (основная или вторая) **или
  Owner**. Столы Owner считаются столами технаря САМИ — месячные вкладки, `deskLoad`, «Технари»,
  дашборд и график; помечать их руками не нужно, и галочка «Стол технаря» у таких столов
  скрыта (снять её всё равно нельзя — признак идёт от роли). Пометка `page.technicianDesk`
  осталась для столов ОСТАЛЬНЫХ ролей (Admin и т.п.). Если понадобится исключить конкретный
  стол Owner из месячных вкладок — поля-выключателя сейчас нет, надо заводить.
- **Виды стола** (`TableViewMode`): «Таблица», «Карточки» (`CardListView.tsx`) и «Канбан».
  Карточки — режим для телефона: одна строка = одна карточка (клиент, сумма, статус, дата,
  телефон, ОС), тап открывает тот же `RowCardSheet`; пустые строки-слоты в список не попадают.
  На экране уже 640px стол по умолчанию открывается карточками — но только пока человек сам не
  переключил вид: выбор пишется в localStorage на каждую вкладку отдельно. Какой столбец
  «клиент», какой «сумма» — общий `utils/rowCardColumns.ts` (канбан берёт оттуда же, чтобы виды
  не разъехались). Переключатель видов виден всегда; кнопка канбана — только при столбце-статусе.
- **Доступ к столу** — один диалог `DeskAccessDialog.tsx` (кнопка «Доступ» с аватарами в шапке
  стола и пункт «⋯ → Доступ к столу»): ответственный, переключатель «открыт для всех / скрыт»
  (то же, что `togglePageVisibility`: открыть = просмотр всем, скрыть = только ответственному),
  ожидающие запросы на просмотр с «Открыть/Отклонить» и список участников с «Просмотр/Правка».
  Пишется одним `updatePageAccess()` (allowedUsers + editableUsers + hiddenByResponsible).
  Owner в списке нет (видит всё всегда), Тимлид без роли Технарь помечен «столы не открывает» и
  переключатели у него выключены (`isDeskBlockedFor`). Старый `EditPageDialog` («Настройки
  страницы») удалён. Кнопки в шапке столбцов (закрепить/⋯/фильтр) на десктопе видны при наведении;
  чипы статусов без строк свёрнуты в «+N».
- **«Заказы»** (`/orders`, `OrdersPage.tsx`, `orderService.ts`, коллекция `orders`) — биржа между ОС
  и технарями, у всех ролей в меню. Выдаёт ОС (и как вторая роль), Тимлид, Owner («Выдать заказ»:
  клиент, номер, цена, ссылка, персы, минуты, пожелания). **ОС выбирают все** из общего списка
  «Ответственный» — и ОС, и Тимлид могут выставить заказ на любого; свой ник (`osNickValue`)
  просто стоит первым с пометкой «вы» и выбран по умолчанию. Технари откликаются (`claims[uid]`, правило пускает
  только свой ключ), выдающий отдаёт заказ одному из них или «Рандом» (среди откликнувшихся со
  столом, иначе среди всех со столом). В заказе есть **дедлайн сдачи** (`deadline`) и
  **срочность** (`urgency`: «Горит» / «Срочный» / «Нейтральный»; нейтральный бейджем не метится).
  Выданный заказ уезжает в стол технаря САМ — `useOrderAutoPickup` в `AppLayout`: подписка
  `assignedUid == me && status == assigned` (одна на сессию, только у технаря со столом; два
  равенства сервер собирает без составного индекса; снимки ИЗ КЭША пропускаются, а
  `takeOrderToDesk` перед записью перечитывает заказ `getDocFromServer` и бросает
  `OrderNotAssignedError`, если он уже не «выдан мне» — см. урок про LRU-кэш ниже; свою строку
  ищет и по `orderRowId`, и по `row.orderId`) пишет строку в текущую месячную вкладку (`ensureMonthTab`)
  через `buildQuickOrderRow` (клиент/номер/цена/ОС/перс/мин/ссылка → столбцы,
  персы-минуты-пожелания-ссылка → визитка) и переводит заказ в `taken`.
  **Дедлайн всегда попадает в визитку клиента** (`row.extras.deadline`) и стоит первым в её чипе
  («до 15 окт. 2026 г. · 2 перс · 3 мин»); поле «Дедлайн сдачи» в визитке редактируется и
  хранится полднем по Алматы. В СТОЛБЕЦ он пишется, только если столбец назван как срок
  (`/дедлайн|сдач|срок/`): обычный столбец-дату `orderDayInMonth` читает как дату ПОЛУЧЕНИЯ
  заказа, и дедлайн ломал «Заказы по дням» и суммы дашборда.
  Подбор столбцов идёт по видимым, но скрытый столбец не съедает значение (`mergeColumnPicks`):
  у цены запасного места в визитке нет. ОС ищется по названию, а если не нашлось — по типу
  `responsible` (читает его `osColumnsOf` именно по типу). Если вкладка месяца из
  `autoMonthSubPageId` удалена — `takeOrderToDesk` БРОСАЕТ ошибку, а не пишет ключами «Основной»
  в несуществующую вкладку. Заезды сериализованы очередью на модуль (`enqueuePickup`): снапшот
  приносит все выданные заказы разом, и параллельные заезды занимали один и тот же пустой слот —
  второй заказ затирал первый. Id строки выводится из id заказа (`orderRowId`), поэтому повтор
  после сбоя и вторая вкладка того же технаря пишут в ту же строку. Столбцы берутся у ТОЙ
  таблицы, куда идёт запись: у месячной вкладки свой набор ключей, и от ключей «Основной» ОС,
  номер и дата приезжали пустыми. Строка занимает первый пустой слот (`isBlankRow`), как
  «Добавить строку» и «Быстрый заказ», и только если слотов нет — дописывается вниз. Статус
  сразу ставится «В работе» (`findInProgressStatusOption` — по названию, списки статусов у
  каждого workspace свои). Пишет именно сессия технаря —
  в чужой стол по правилам не может писать никто, кроме Owner и ответственного; если технарь не
  в сети, заказ приедет при первом открытии приложения. Кнопка «Забрать в стол» на «Заказах»
  осталась запасной (нет стола / автозапись упала). Новая строка помечена `row.highlight` и
  подсвечена в таблице (`.table-row-new`), снимает подсветку только сам технарь — чип
  «N новых · снять» в тулбаре (`clearRowHighlights`, один batch). Цвет подсветки —
  **ЯНТАРНЫЙ** (`--warning`), не акцентный: акцентом подсвечены выделение, активная ячейка и
  «добавлено недавно», и приехавший заказ путался с собственной строкой. В таблице это
  заливка строки плюс полоса слева, у визитки клиента — янтарный чип вместо фиолетового
  (`clientCard.isNewOrder`), в «Карточках» и «Канбане» — янтарная рамка и подпись **«НОВЫЙ»**
  (не только цвет: подпись читается и в ч/б, и тем, кто цвета различает плохо). В карточке
  подпись стоит в строке мета-данных, а не у заголовка — там она съедала имя клиента. Отдельно от подсветки есть
  ПОСТОЯННАЯ метка `row.orderId` (ставится и при занятии пустого слота — `markRowOrder`): строка
  с биржи навсегда отличается цветом — фиолетовый чип визитки в таблице и фиолетовая рамка в
  «Карточках» и «Канбане». Подсветка новой строки перекрывает её, пока её не сняли. Так и через
  месяц видно, что заказ пришёл с «Заказов», а не заведён руками.
  **Уведомление о новом заказе доходит ДО человека, а не только до колокольчика**
  (`utils/browserNotify.ts`, `hooks/useNotificationAlerts.ts`). `createOrder` как и раньше
  пишет по документу-уведомлению каждому Технарю (`memberHasRole(m,'manager')`, вторая роль
  считается), в теле — срочность, дедлайн, цена и ОС: во всплывашке браузера видно только
  заголовок и две строки. Дальше мост в `AppLayout`: звук (WebAudio, один на пачку) плюс
  **всплывашка браузера**, если вкладка свёрнута или окно не в фокусе
  (`visibilityState`/`hasFocus` — окно на втором мониторе формально «видимо»), и обычный тост,
  если человек и так смотрит на экран. Мост стоит в `AppLayout`, а НЕ в колокольчике: в
  полноэкранной таблице ни сайдбара, ни шапки нет — то есть ровно там, где технарь и сидит.
  FCM/push тут нет (Spark), уровень честный: «пока вкладка открыта, пусть и свёрнута».
  Что «новое» — `pickFreshNotifications` (`utils/freshNotifications.ts`): создано позже
  открытия вкладки (запас 2 мин на расхождение часов устройств) и ещё не показывалось
  (память в `sessionStorage`). Не «чего не было в прошлом снимке»: подписка сначала отдаёт
  пустой массив, и на втором снимке всплыло бы всё за месяц (10 юнит-проверок).
  Разрешение спрашиваем ТОЛЬКО по клику — без жеста браузер молча отказывает, и второй раз
  спросить уже нельзя: кнопка в выпадашке колокольчика (`BrowserNotifyRow`) и плашка на
  «Заказах» у технарей (`OrdersNotifyBanner`). Выключатель человека
  (`nova:browser-notify` в localStorage) общий на оба места через
  `subscribeBrowserNotify`/`useSyncExternalStore` — со своим `useState` у каждого выключение
  в колокольчике не возвращало плашку на «Заказах». На iPhone в обычной вкладке
  `Notification` нет вовсе — там остаются звук и тост, поэтому `supported()` проверяется
  везде. Заодно подписка на свои уведомления стала ОДНОЙ на приложение
  (`useNotifications` считает читателей): колокольчиков на десктопе два, плюс мост — было бы
  три слушателя и три показа одного уведомления.
  **«Рандом» крутит барабан** (`components/orders/RandomWheelDialog.tsx`): колесо с именами
  тех, кто в пуле, стрелка сверху, победитель остаётся, остальные сектора гаснут, конфетти.
  Победителя выбирает `pickFromPool` (crypto) ДО показа, колесо докручивается ровно до его
  сектора (5 оборотов + сдвиг внутри сектора, не больше 12°, чтобы подпись под стрелкой не
  вставала боком). Наоборот — «куда остановится, тот и выиграл» — нельзя: браузер не
  гарантирует ни длительности анимации, ни того, что свёрнутая вкладка её вообще проиграет.
  Пул и победитель ФИКСИРУЮТСЯ в момент броска и живут в состоянии страницы: заказ за время

  «Грок» / «Хикс» (Higgsfield) / «11 Labs» (ElevenLabs) и «Другие» (Suno и прочее, только если есть)
  с «доступно N / всего» и ближайшим восстановлением. Раздел — `?s=grok|higgsfield|elevenlabs|other`
  (помнится в localStorage), старый `/grok-limit/apps` редиректит на `?s=higgsfield`. Поиск («/»)
  ищет сразу по всем разделам. Строка аккаунта — `GrokPoolRow` (общая для `grokAccounts` и
  `grokAppAccounts`): «Кончился» → пресет времени восстановления, «Доступен» → сброс, логин/пароль
  копируются из строки.
  **Доступ к аккаунту подписки** (`grokAppAccounts.restricted` + `allowedUids`): Owner/Тимлид в
  меню строки открывает «Доступ к аккаунту» и отмечает людей — остальные аккаунт не видят
  вообще. Пустой список = аккаунт снова открыт всем. Правило чтения смотрит поля НАПРЯМУЮ (см.
  урок про `.get()` ниже), поэтому у документа поле `restricted` обязано быть: новым его пишет
  сервис, старым — разовый `backfillGrokAppRestricted` из сессии руководства (оно одно читает
  коллекцию целиком). Из-за этого у не-руководства ДВА запроса вместо одного — «открытые»
  (`restricted == false`) и «мои» (`array-contains uid`), результат склеивается: list-запрос
  падает целиком, если в выдачу попадает закрытый документ. Технарь по-прежнему отмечает лимиты
  у доступных ему аккаунтов, но `restricted`/`allowedUids` не трогает (`grokAppAccessPreserved`
  в правилах). Проверено эмулятором — 20 проверок (`grokaccess.mjs`), включая «через список
  пароль закрытого не утекает».
  **Право «управляет разделом»** (Хикс / 11 Labs / Другие; `grokSettings/access` →
  `managers[provider] = uid[]`, `types/grokAccess.ts`) — ОТДЕЛЬНОЕ от ролей право страницы, так
  просил Nurba: роль (Технарь, ОС, Тимлид) решает только, пускают ли на страницу. Назначает
  ТОЛЬКО Owner («Кто управляет» в строке над списком раздела). Закрывать/открывать аккаунт и
  решать запросы может Owner или управляющий провайдером (`canGrantGrokApp` в правилах) —
  Тимлид как таковой больше НЕТ (видеть все аккаунты он по-прежнему может). Ключ — `provider`
  аккаунта, а не раздел: в языке правил нет тернарного «раздел провайдера», поэтому «Другие»
  пишутся под двумя ключами (`suno` и `other`). Управляющий читает все аккаунты своих
  провайдеров отдельным запросом `where provider == X` (правило чтения проверяет
  `isGrokManager(resource.data.provider)` — значение берётся из фильтра). Менять провайдер
  аккаунта вместе со списком доступа можно, только если управляешь и старым, и новым.
  **Витрина закрытых** (`grokAccessStubs/{accountId}`: provider, providerOther, title — БЕЗ
  логина и пароля; title = название или почта `an•••@gmail.com`) — чтобы технарь мог запросить
  то, чего не видит: закрытый аккаунт ему не прочитать. Пишется той же пачкой, что и
  `setGrokAppAccess`, а ещё сверяется из сессии Owner/управляющего (`syncGrokAccessStubs`):
  так она заводится для уже закрытых аккаунтов, следует за переименованием и чистится, когда
  аккаунт удалил технарь (витрину он трогать не вправе). Сверка — только когда список
  аккаунтов ПОЛНЫЙ (`complete`: все запросы ответили с сервера; отказ одной части полноту
  снимает) — иначе удалилась бы карточка живого аккаунта.
  **Запрос на доступ** (`grokAccessRequests/{accountId}_{uid}`): пишет сам человек — за себя и
  только `pending`, повтор после отказа перезаписывает тот же id, «Отозвать» удаляет. Уведомление
  (`kind: grok-access-request`) уходит управляющим провайдера и Owner. «Открыть доступ» —
  `arrayUnion` в `allowedUids` + статус ОДНИМ batch (флаг `restricted` не трогаем: если аккаунт
  тем временем открыли всем, «закрыт на одного» отрезал бы остальных); закрыт ли аккаунт —
  из самого аккаунта, а если он не пришёл в список — из витрины. Сам запрос прав не даёт:
  подложить в него чужой провайдер бесполезно — запись в `allowedUids` правило пустит только
  управляющему настоящего провайдера аккаунта; кроме того, провайдер запроса правило сверяет с
  карточкой витрины.
  **Уроки ревью (проверено эмулятором, 19 проверок `grok2.mjs` + 42 исходных):**
  ЗАКРЫТЫЙ аккаунт правит/удаляет только тот, кто его читает (`canTouchGrokApp`), и его
  `provider` меняется только с правом на оба раздела (`grokProviderChangeOk`) — иначе id из
  витрины хватало, чтобы merge `{provider}` перенёс чужой аккаунт к «своему» управляющему, и
  тот читал пароль. В панели запросов имя и аккаунт показываются НЕ из запроса (их пишет сам
  просящий — «Анна Петрова → Хикс тест»), а из участников по uid и из витрины/аккаунта по id.
  Удаление несуществующей карточки витрины разрешено (`resource == null`): у открытых аккаунтов
  её нет, и пачка «удалить аккаунт + карточку» падала целиком. `backfillGrokAppRestricted` пишет
  `updatedByUid` — без него правило правки отказывало всей пачке молча. Полнота списка
  аккаунтов привязана к КЛЮЧУ подписки (workspace|права|управляемые провайдеры), витрина — к
  workspace: при смене прав старый «полный» флаг сверил бы витрину со старым списком и удалил
  живые карточки. Повтор сверки — только после успеха; чужую карточку (не мой провайдер) сверка
  не переписывает — отказ одной записи иначе ронял бы пачку по кругу. Диалог доступа пишет
  РАЗНИЦУ поверх живого списка: иначе сохранение отнимало доступ, выданный по запросу, пока
  диалог был открыт. Управляющими нельзя назначить чистого ОС — страница ему закрыта.
- **«График»** (`/schedule`, `SchedulePage.tsx`, пункт меню у всех ролей; документы
  `techSchedule/{uid}_{monthKey}`) — отдельный раздел на ВСЕХ сменных, четыре секции с чипами-
  фильтрами сверху: **«Технари»** (`worksAsTechnician` — Технарь или Owner; плюс запасной путь
  «ответственный за живой стол» для остальных ролей), **«ОС»**, **«Руководство»**
  (Owner и Тимлиды) и **свой раздел** (см. ниже). Человек стоит ОДИН раз, в первой подходящей
  секции: график хранится по uid, и две строки на один документ означали бы, что правка в одной
  молча меняет вторую. Список столов у каждого свой, поэтому «человек со столом, но без роли
  Технаря» у одних попадёт в «Технари», у других — в «Руководство»; в графике он есть в любом
  случае. Сетка — `components/schedule/ScheduleGrid.tsx` (она же даёт `ScheduleLegend`): под
  числом стоит день недели, справа колонка «В» — сколько выходных за месяц, **своя строка
  подсвечена** (имя акцентом + чип «вы» + заливка строки; липкой колонке подсветку задаём
  ОТДЕЛЬНО — она рисует свой фон поверх строки и не наследует её), **сегодняшний день** — число
  в залитом кружке плюс подсветка всей колонки (тонкой рамки вокруг клетки в сетке на 31
  колонку было мало), а над сеткой стоит строка «Сегодня 21 сентября, понедельник» и своё
  состояние на сегодня («рабочий день · смена 12:00–15:00» / «выходной» / «отпросились»).
  На телефоне сетка
  сама доскроллена до сегодняшнего дня, а ширина колонки с именами ограничена жёстко (без
  потолка `truncate` не срабатывает и сетки секций разъезжаются по дням). Месяц листается
  стрелками. Диалога «График» на «Технари» больше нет — там осталась кнопка-ссылка сюда,
  и подписку `useTechSchedules` та страница не держит.
- **Свой раздел графика** (`scheduleGroups/custom`, `scheduleGroupService.ts`,
  `types/scheduleGroup.ts`) — название задаёт Owner/Тимлид прямо в заголовке секции, люди в нём
  НЕ участники workspace (подрядчики): аккаунта и роли у них нет, а смены есть. Документ пишется
  ЦЕЛИКОМ (`name` + `people`), потому что правило проверяет `hasOnly` ровно по этому набору
  ключей — частичный merge разошёлся бы с ним на первой же записи. У такого человека нет uid,
  поэтому график ему кладут под синтетическим `ext_…` (`newSchedulePersonId`): правило
  «участник правит свой `selfWork`» сравнивает `resource.data.uid` с `request.auth.uid` и на
  таком id не совпадёт никогда — значит, эти смены ведёт только руководство. Проверено
  эмулятором (13 проверок: кто пишет раздел, кто читает, лишний ключ, чужой workspaceId,
  и что технарь не дотянется до `ext_`-графика). Удаление человека из раздела НЕ трогает его
  документы `techSchedule` — вернуть того же человека под тем же именем и получить старые
  смены нельзя, id будет новый.
  **Человек «в ожидании аккаунта»**: у `SchedulePerson` есть `osNick` — ник ОС, за которым его
  закрепили заранее. Когда этот ник (ОС или технаря — имя строки сравнивается тоже)
  закрепляют за живым участником — `NickDialog`, «Привязать» на «Команде» (`NickListCard`) или одобрение
  заявки с ником (`adoptScheduleRowByNick`), сразу следом идёт `bindScheduleGroupPersonToMember`: ОДНОЙ транзакцией
  его неделя переезжает под uid участника, а «ожидающая» строка исчезает из раздела (иначе один
  человек остался бы в графике дважды, с двумя разными неделями). `appliedThrough` у
  перенесённой недели снимается — месяцы разложены на старый `ext_`-id, автопилот разложит их
  заново под uid; месячные `techSchedule/{ext_…}` НЕ переносятся (id там по uid), прошлые дни
  остаются историей «ожидающего». Во вставке недели из таблицы у нераспознанного имени есть
  пункт «+ завести «Имя»» — заводит такого человека (имя = ник ОС) прямо из диалога.
  Проверено эмулятором (`adopt.mjs`): Тимлид переносит, технарь — нет, чужая строка недели не
  тронута, второй «ожидающий» остаётся на месте.
  **График целиком ведёт руководство** (Owner/Тимлид, `canRetireDesks`), технарь и ОС его
  только читают — в правилах у них НЕТ ни одной ветки на запись (была: свой `selfWork`; убрана
  — это состояние перебивает выходной, поставленный Тимлидом). Кнопки «Вышел на смену» больше
  нет ни в графике, ни на «Заказах»: там, где отклик закрыт, написано «отметить выход может
  Тимлид».
  Правится график ДВУМЯ разными путями, и это намеренно:
  - **Режим правки** (кнопка «Редактировать») — выходные на месяц вперёд. Клик по дню ставит
    и снимает ТОЛЬКО выходной и копится в ЧЕРНОВИКЕ на клиенте (`draft`, ключ `uid:день`);
    в базу всё уезжает по «Сохранить» ОДНИМ batch (`saveScheduleDraft`). День, возвращённый к
    исходному значению, из черновика удаляется — лишних записей нет. Месяц в этом режиме не
    листается (черновик привязан к месяцу), «Отмена» спрашивает подтверждение, если есть
    несохранённые дни.
    Здесь — только РАЗОВЫЕ исключения (отпуск, «поменялись»). Постоянные выходные по дням
    недели ставятся не тут, а во вкладке «Неделя» (ниже); старый одноразовый «Шаблон недели»
    (`WeekPatternDialog`/`schedulePattern.ts`) удалён — его приходилось раскладывать заново
    каждый месяц на каждого человека, на что Nurba и жаловался.
  - **Вкладка «Неделя» — постоянный распорядок** (`types/scheduleTemplate.ts`,
    `utils/weekTemplate.ts`, `services/scheduleTemplateService.ts`, `WeekTemplateGrid`,
    `WeekPasteDialog`). Это та же таблица, что руководство вело в Google Sheets: люди по
    строкам, Пн…Вс по колонкам, «работа / вых / с 12:45 / 12:30–15:00», внизу «На смене» по
    дням. Хранится ОДНИМ документом `scheduleTemplates/week` (`people[id] = { days: {dow: "off"},
    hours: {dow: {from,to,label?}}, appliedThrough }`, dow — `getUTCDay()` строкой, «0» = вс):
    его читает каждый, кто открыл «Неделю», и 40 документов вместо одного на Spark — лишнее.
    Слушатель висит только пока открыта вкладка «Неделя». «График» ВСЕГДА открывается на
    «Неделе» (просьба Nurba), выбор «Месяц» не запоминается: иначе у того, кто хоть раз открыл
    месяц, неделя по умолчанию пропала бы навсегда. Плашка «сегодня у вас выходной · попросить
    отметку» видна в обоих видах — на неё ведёт ссылка с «Заказов».
  - **«Мой график»** (`MyScheduleCard`) — свой график крупно и отдельно над общей сеткой, в
    обоих видах, у всех, кто сам есть в графике (Viewer/Admin без стола видят только дату).
    Показывает РЕАЛЬНЫЕ дни этой и следующей недели (чипы «Эта / Следующая») из месячного
    `techSchedule` — с исключениями, «отпросился», «вышел в выходной» и часами, а не недельный
    шаблон: шаблон не знает про отпуск в четверг. Неделя может перейти через месяц, поэтому
    карточка держит точечные слушатели своих документов за каждый месяц окна
    (`subscribeTechSchedule`, 1–2 штуки) и не зависит от месяца, открытого в сетке. На
    телефоне дни идут списком, на десктопе — семь плиток.
    **Неделя — не второй источник правды.** «Заказы», «Технари» и дашборд по-прежнему читают
    ТОЛЬКО месячные `techSchedule`: сохранение недели сразу раскладывает её туда — остаток
    текущего месяца с СЕГОДНЯШНЕГО дня (прошлые дни — история, не трогаем) и весь следующий,
    одним batch вместе с самой неделей. Месяцы дальше раскладывает автопилот
    `useWeekTemplateAutopilot` (AppLayout, только сессия руководства по НАСТОЯЩЕЙ роли,
    раз на загрузку): у кого `appliedThrough` меньше следующего месяца — доразложить. Обычно
    это одно чтение и ноль записей; 1-го числа он заполняет новый «следующий» месяц.
    Раскладка (`layWeekOnMonth`) переписывает ТОЛЬКО дни, которые шли по ПРОШЛОЙ неделе:
    выходной или часы, поставленные в месяце руками, — исключение и переживают смену недели
    (ручные часы делают исключением ВЕСЬ день — проверка стоит до решения о выходном, иначе
    неделя с новым выходным стирала согласованные полдня);
    для месяца, который ещё не раскладывали, «прошлая неделя» = «все дни рабочие», так что
    ручные выходные переживают и первую раскладку. «Отпросился» и «пришёл» (`selfWork`) не
    трогаются никогда. Выходной → рабочий снимает и забытые под выходным часы. Месячные
    документы для раскладки читаются `getDocFromServer`/`getDocsFromServer`: кэш без сети
    отдал бы пустоту, и раскладка стёрла бы разовые отметки. Правка недели выключена, пока
    сама неделя не пришла с сервера (`templateReady`) — по той же причине.
    Запись человека в неделе — все семь дней ЯВНО (значение или `deleteField()`), через
    `setDoc(merge)`: вложенные карты при merge сливаются, и без явного удаления снятый выходной
    остался бы в документе; пустых карт при этом не бывает.
    **Правка — кистью** в режиме «Изменить неделю»: «Выходной» / «Рабочий» / «Смена с/до»
    (конец можно не указывать — «с 12:45»), клик по клетке красит, клик по дню недели в шапке
    — весь столбец раздела. Повторный клик той же кистью ВОЗВРАЩАЕТ к сохранённому, а не в
    «работу» (промах по столбцу иначе стирал людям настоящие выходные). Черновик (`weekDraft`)
    хранит только ТРОНУТЫЕ дни, а не снимок недели: сохранение = неделя с сервера сейчас +
    тронутые дни, и правка другого руководителя в другие дни не откатывается. Пока идёт
    сохранение, кисть и вставка выключены (иначе правки молча терялись при сбросе черновика).
    Месяц и день для раскладки берутся из ОДНОГО чтения часов в момент сохранения (и в
    автопилоте): `useCurrentMonthKey` отстаёт до минуты, и в первую минуту 1-го числа пара
    «прошлый месяц + день 1» переписала бы весь прошедший месяц.
    **Вставка из Google Sheets / Excel** — кнопка «Вставить из таблицы» или просто Ctrl+V на
    вкладке «Неделя» (слушатель `paste` на документе, поля ввода не перехватывает). Буфер
    режется как TSV С КАВЫЧКАМИ (`splitTsv`): клетка с переносом строки приходит в кавычках,
    и резать по `\n` до кавычек нельзя — неделя съезжала. Заголовок — строка, где есть хоть
    один день недели и нет клеток-значений (так узнаётся и блок из одних «Сб | Вс»); дни
    сравниваются ЦЕЛЫМ словом (префикс ловил «Всего» как «Вс» и «Среднее» как «Ср»), повтор
    дня — берётся первая колонка. Имя — колонка с подписью «Имя/ФИО/Сотрудник», иначе
    ближайшая к дням колонка с буквами («№» и «Раздел» слева не мешают). Строки
    «люди на смене»/«итого» пропускаются. Клетки: «работа», «вых», «с 12:45», «12:30 до 15:00»,
    «с 11 до 18», «15:30», «10-12,15-19» (несколько отрезков сортируются, налезать не должны;
    хранится `from` первого, `to` последнего и `label` для показа). Грамматика СТРОГАЯ: кроме
    времени — только «с/от» в начале и «-/до/по» между, число без двоеточия и без «с» — не

- **Ники — одна модель на три вида** (`NickKind = "os" | "tech" | "other"`, `NICK_KIND_META`,
  `linkMemberNick`, `resolveNickOption`, `addNickOption`, `setNickOptionInactive` в
  `memberService.ts`; UI — `NickDialog`/`NickPicker`). У каждого вида ОТДЕЛЬНЫЙ список:
  ник ОС — `responsibleOptions` + `osNick`/`osNickValue`, ник технаря — `techNickOptions` +
  `techNick`/`techNickValue`, ник «Другие» — `otherNickOptions` + `otherNick`/`otherNickValue`.
  Ники технарей в «Ответственный» класть нельзя: любой столбец «Ответственный» считается
  ОС-столбцом (`osColumnsOf`), и технари посчитались бы как ОС в заказах, оценках и на дашборде.
  Какой ник положен человеку — `nickKindsFor()`: ник его раздела, плюс ник ОС всем с ролью ОС
  (это ключ заказов, а не подпись — Admin + ОС стоит в «Других», но ник ОС ему нужен). Ник,
  оставшийся от прошлой роли, показывается жёлтым чипом «не по роли» (`nickKindsShownFor`) —
  открепить его можно (у Owner/Admin, которые всё ещё работают за столом, это не «от прошлой
  роли», а «вне раздела»). **Человек работает под ником:** `displayNameOf`/`personLabel` берут
  рабочий ник ПЕРВЫМ (`workNickOf`), поэтому его так видно везде — «Технари», «Заказы»,
  «График», столы, «Люди»; `myDisplayName` делает то же для своих действий. Если у человека
  есть и ник технаря, и ник «Другие» (Owner держал ник технаря, пока стоял в технарях), подписывает
  ник ЕГО раздела — иначе новый ник ничего бы не менял, пока старый не открепят. Ник ОС в
  подпись не идёт. Перенос строки графика «ожидающего» (`adoptScheduleRowByNick`) по нику
  «Другие» — только для Owner и Тимлида: Admin и Viewer без стола в графике не показываются. Ники не переименовываются и не удаляются, только «неактуальные»; списки пишутся
  транзакцией, потому что массив всегда переписывается целиком.
  **При выдаче ника занятое не показывается** (просьба Nurba): в `NickPicker` ники,
  закреплённые за ДРУГИМ аккаунтом, скрыты (внизу «скрыты · N»; если ввести такой ник целиком —
  строка «уже закреплён за …», чтобы не казалось, что он пропал), а в «Привязать» у свободного
  ника — только люди раздела, у которых ника этого вида ещё нет; сменить ник человеку с ником —
  из его строки. Уникальность держит не UI, а `assertNickFree` (свежий запрос к серверу перед
  транзакцией) + `assertSameNick` внутри неё.
  Тимлид не ставит ник сам себе и не трогает ник Owner (`nickLockedFor`; self-lock в правилах
  members включает `osNick*`/`techNick*`/`otherNick*`, запись об Owner Тимлиду закрыта целиком);
  самому человеку поле не писать, приглашение с ником отклоняется. Одобрение заявки выдаёт ник
  раздела выбранной роли (`nickKindForRole`: Технарь → технаря, ОС → ОС, Тимлид/Admin/Viewer →
  «Другие»). Проверено эмулятором — 34 проверки (`nicks.mjs`): заявка только Технарь/ОС и без
  лишних ключей, одобрение одной пачкой (и как Viewer с ником «Другие»), Тимлид не ставит свой
  ник и ник Owner, Owner себе — может, приглашение без ников, самосоздание участника закрыто.
- **Полное удаление человека — только Owner** (`deleteMemberCompletely`, кнопка с иконкой
  «человек-крестик» на «Пользователях»; у Тимлида там осталось обычное «Убрать из workspace»,
  две кнопки рядом не ставим — разница между ними не видна). Чистит всё, что привязано к
  АДРЕСУ и аккаунту, ОДНИМ batch: участник `members/{uid}`, приглашение по почте
  `members/{email}`, ВСЕ заявки на вход с этим адресом (и по uid, и запросом
  `where email ==` — человек мог подаваться с другого аккаунта на ту же почту) и
  `deskObservers/{uid}` (иначе, вернув человека, ему молча вернулись бы чужие столы на чтение).
  Батч атомарный: половинчатое удаление — участника нет, а заявка «одобрена» висит — это ровно
  то состояние, из-за которого человек потом не может ни зайти, ни подать заявку заново.
  **НЕ трогает стол и ник** (так просил Nurba): стол остаётся со своим `responsibleUserId`,
  строками и вкладками, ник остаётся вариантом в списке workspace — подписи и цвета в старых
  заказах резолвятся как раньше. Доступа это не даёт: и `isResponsiblePage`, и ветка
  `allowedUsers` в правилах требуют членства. Owner-only держат САМИ ПРАВИЛА, а не UI:
  `deskObservers` пишет только Owner, и батч Тимлида отклоняется целиком. Правила не менялись.
  Чего убрать нельзя: `users/{uid}.workspaceIds` — это чужой профиль, его не пишет никто, кроме
  хозяина, поэтому workspace остаётся у него в списке и открывается экраном «вас убрали» с
  кнопкой «Убрать из моего списка». Проверено эмулятором — 14 проверок (`deluser.mjs`):
  технарь и Тимлид полное удаление не проводят, Owner проводит; стол, строки и ник на месте;
  участника, приглашения, обеих заявок и тихого доступа нет; удалённый не читает свой бывший
  стол и может подать заявку заново.
- **Ошибки базы человеку — с кодом** (`utils/dbError.ts`): `firestoreErrorText` переводит код
  Firestore в русскую строку и ДОБАВЛЯЕТ сам код («…не хватает прав (permission-denied)»), свои
  собственные throw'ы («Ник уже есть в списке») оставляет как есть. Без кода три разных отказа —
  нет прав, нет связи, список разъехался — выглядели одинаковым «не удалось», и починить по
  такому сообщению нельзя. Подключено ко всем операциям с никами и к одобрению заявки.
  **22.09.2026 этот же текст и нашёл настоящую причину «не добавляются ники и не одобряются
  заявки»: `resource-exhausted` — кончилась ДНЕВНАЯ КВОТА бесплатного Firebase (Spark: 50k
  чтений и 20k записей в сутки), и в приложении не проходила ни одна запись.** Ники ни при чём.
  Главный пожиратель чтений — `useOwnerDeskRecount`: сессия Owner ЧИТАЛА ВСЕ СТРОКИ месячной
  вкладки КАЖДОГО стола каждые 5 минут, пока открыт дашборд или «Технари» (15 столов × ~100
  строк = ~18 000 чтений в час — дневная квота за три часа). Теперь стол пересчитывается, только
  если его счётчики старше 2 часов или относятся к другой вкладке: пока технарь работает, его
  сессия публикует их сама. Квота сбрасывается в полночь по тихоокеанскому времени (≈13:00 по
  Алматы); настоящее решение — тариф Blaze, где бесплатные квоты те же, а сверх них платится
  по факту. **Удаление данных квоту НЕ возвращает** — это счётчик операций за сутки, а не
  место (тот же код `resource-exhausted` даёт и переполнение 1 ГиБ хранилища на Spark, и вот
  там удаление как раз помогает; какая из двух — видно в консоли Firebase → Usage). Первый же
  такой отказ поднимает общий флаг (`dbQuotaHit` в `utils/dbError.ts`) и полосу
  `DbQuotaBanner` в `AppLayout`: иначе это выглядит как набор несвязанных поломок, у каждого
  своя — не сохранилась ячейка, не одобрилась заявка, не встал статус. Полосу можно скрыть, но
  следующий отказ поднимет её снова: пока квоты нет, это правда, а не уведомление. 9
  юнит-проверок.
  **Правка ячейки больше НЕ стоит две записи.** Стоила: сама строка плюс отдельный документ
  истории (`logChange` в `updateRowCell`) — половину дневной квоты записей съедал журнал.
  Теперь записи истории копятся в памяти и уезжают ПАЧКОЙ в ОДИН документ
  (`historyService.ts`: буфер на workspace, сброс через 10 с, при 50 записях, при уходе со
  вкладки — `visibilitychange`/`pagehide` — и перед перезагрузкой на новую версию в
  `reloadSafely`). Квота Firestore считается по ДОКУМЕНТАМ, а не по вызовам, поэтому
  `writeBatch` тут не спас бы вовсе: тридцать записей одной пачкой стоят тридцать записей —
  экономит ТОЛЬКО объединение в один документ. Цена — окно в 10 секунд: оборванная вкладка
  унесёт последние записи ЖУРНАЛА (строки таблицы пишутся как и раньше, сразу). Документ
  коллекции `history` теперь бывает двух видов — старый (одна запись прямо в документе) и
  новый (массив `entries`); разворачивает оба `expandHistoryDoc` (`utils/historyDocs.ts`),
  порядок внутри пачки восстанавливает `sortHistoryDesc`. Старые документы не переписывали.
  Правило `history` в firestore.rules не менялось: там только `create`, а пачка и есть create
  под новым id. Проверено: 13 юнит-проверок разбора документов и 16 проверок настоящего
  сервиса против эмулятора (30 правок = 0 документов до сброса и ровно 1 после, автосброс на
  50-й, чужой workspace в чужом документе).
    **Транзакция Firestore без связи НЕ падает — она висит** (ей нужен ответ сервера, очередь
  офлайн-записей транзакциям не помогает), и кнопка остаётся в «сохраняю…» навсегда. Поэтому
  `withDbTimeout` (15 с) обёрнут вокруг `addNickOption`, `setNickOptionInactive`,
  `linkMemberNick`, `approveJoinRequest` и обоих серверных чтений `assertNickFree`
  (`getDocFromServer`/`getDocsFromServer` висят так же). 12 юнит-проверок.
  Сами правила и сервисы ников проверены и ЭМУЛЯТОРОМ, и прогоном настоящего кода сервисов
  против эмулятора (добавить ник, одобрить заявку новым и существующим ником, выдать/сменить/
  снять ник у участника) — там всё проходит: если в проде «не добавляется», причина видна
  теперь в тексте тоста.

- **Ник ОС** (`members.osNick`/`osNickValue`): вариант общего списка «Ответственный».
  Закрепляет Тимлид/Owner на «Команде» или «Пользователях» (`NickDialog kind="os"`): сначала
  выбор из уже существующих ников (на них могут висеть месяцы заказов), новый — дописывается в
  список. Существующие варианты **никогда не переименовываются и не удаляются** — так просил
  Nurba. Самому ОС поле не писать (self-service правило members его не пускает).
- **Неактуальные ники ОС** (`StatusOption.inactive`, `splitOptionsByActivity` в
  `utils/columnOptions.ts`) — то, чем «увольняют» ОС вместо удаления варианта. Флаг ставят Owner
  и Тимлид в редакторе вариантов (`ManageOptionsDialog`: кнопка-архив «В неактуальные»/«Вернуть»
  вместо крестика; крестик остался, но рядом висит предупреждение). Что меняется: **только
  быстрый выбор**. Вариант остаётся в `responsibleOptions` навсегда, поэтому подпись и цвет уже
  сохранённых значений резолвятся как раньше — и в этом месяце, и в прошлогодних вкладках.
  `getColumnOptions` **никогда не фильтрует** `inactive`: под ним сидят `StatusBadge` (без
  варианта рисует «—»), группировка, фильтры, поиск, CSV, копирование, канбан, карточки,
  `techLoad`/`deskLoad`/`osOrders` и право ОС ставить оценки (`osLastOrderAt`). Фильтрует
  ТОЛЬКО пикер, в пяти местах: ячейка (`TableCell`), карточка строки (`RowCardSheet`), «Быстрый
  заказ» (`QuickOrderDialog`), «Заполнить» у выделенных (`BulkActionBar`) и быстрый выбор первой
  буквой (`DataTable`). В выпадашках внизу стоит кнопка «Неактуальные ОС · N» — обычная
  `<button>` с `preventDefault` на pointerdown (не `SelectItem`: тот закрыл бы список), она
  дорисовывает скрытые варианты, и выбрать ушедшего можно осознанно. Значение, уже стоящее в
  ячейке, из основного списка не убирается (`keepValues`), иначе человек открывал бы выпадашку
  и не видел в ней того, что выбрано. Связку участник↔ник флаг НЕ рвёт: `osNickValue` остаётся,
  ОС продолжает видеть свои заказы и менять старые оценки; «уволить по правам» — это по-прежнему
  «Открепить» или снятие роли ОС. Закрепление неактуального ника за живым аккаунтом снимает флаг
  (ник снова в работе) той же транзакцией. Ключ `inactive` у актуального варианта не пишем
  вовсе: `undefined` внутри элемента массива роняет запись всего списка
  (`ignoreUndefinedProperties` выключен), а `false` осел бы мусором. Правила Firestore не
  менялись — массив лежит в документе workspace, который и так пишут только Owner и Тимлид.
- **Оценки технарей — ДВЕ независимые шкалы, обе ПОМЕСЯЧНЫЕ.** В новом месяце счётчики
  начинаются с нуля, а итог прошлого месяца закрепляется карточкой `MonthlyRatingTop` сверху
  на «Технари» и на «Дашборде» (топ-3 по каждой шкале отдельно, сводного балла нет — вес никто
  не задавал). Без этой карточки первого числа экран выглядел бы как поломка.
  - **Общая** (`techRatings/{osUid}_{technicianUid}_{monthKey}`, 1–5) — одна от ОС каждому
    Технару за месяц, внутри месяца меняется свободно. Оценки, поставленные до перехода на
    помесячные, лежат под старым id без месяца: `ratingMonthKey()` относит их к месяцу их
    `createdAt`, а `rateTechnician` правит звёзды ТОЛЬКО когда `existing.id` совпал с
    месячным id — иначе `updateDoc` ушёл бы в несуществующий документ.
  - **По заказам** (`orderRatings/{pageId}_{rowId}`, 1–5) — оценка конкретного заказа, ставит
    её ОС в «Технари» → «Мои заказы» (повторный клик по той же звезде снимает). Читают только
    Owner, сам ОС и сам технарь: внутри лежит название заказа, а Тимлид содержимого столов не
    видит (как `osOrders`). Среднее НЕ считается по этой коллекции — она растёт на каждый
    заказ; для него есть `orderRatingTotals/{osUid}_{technicianUid}_{monthKey}` (count/sum,
    читают все участники, пишет сам ОС ОДНОЙ транзакцией вместе с оценкой — это счётчик,
    «прочитал-посчитал-записал» его разъезжает). Правила держат `count >= 0` и
    `count <= sum <= count*5`, то есть накрутить среднее выше 5 нельзя.
  - Право оценивать у обеих шкал одно: недавний заказ с ником этого ОС —
    `deskLoad.osLastOrderAt[osNickValue]` моложе 30 дней (день последнего создания/правки
    такого заказа; переживает смену месяца — `publishDeskLoad` в транзакции сливает старые
    значения, держит 40 дней). Окно продублировано в `OS_RATING_WINDOW_MS` и в
    `hasRecentOrderFrom()` — меняй оба. Удалить может Owner/Тимлид (и ОС — свою оценку
    заказа); удаление идёт транзакцией, иначе итоги останутся считать удалённое.
  - Цвет — единственное, чем шкалы различаются визуально: общая янтарная, по заказам
    фиолетовая (`StarRating tone`, `RatingScore`). Форма у обеих звёзды намеренно.

  Чипы под шапкой — `pageChipClass(on, activeTone?)`, не свои классы. Класс `.page-header` в
  `index.css` — ДРУГОЕ: это плоский тулбар для страниц с собственным скроллом (стол, чат,
  Грок), из-за похожего имени его дважды брали под заголовок раздела.
- **Скругления идут по шкале** `--radius: 0.5rem` → 4/6/8/12/16 (`sm/md/lg/xl/2xl`). Значения
  вне шкалы не писать: раньше `2xl` не было в конфиге и 27 карточек брали дефолт Tailwind 16px
  рядом с диалогами по 2px — это и читалось как незаконченный интерфейс.
- **Брейкпойнты Tailwind меряют ВЬЮПОРТ, а не контейнер.** `sm:flex-row` внутри узкой правой
  панели (`max-w-md`) на широком экране схлопывал поле email до 130px; там, где компонент живёт
  в узком контейнере, раскладку задавать без `sm:`. По той же причине сетка карточек на
  «Технарях» — `auto-fill` по ширине колонки, а не `xl:grid-cols-3`.
- **`flex-1` без `min-w-0` не сжимается** меньше своего контента — так строка участника на
  390px оставляла блоку с именем ноль пикселей, и имя с email не рисовались вовсе.
- **Тач-цель — 44px** там, где по элементу реально жмут с телефона (`min-h-11` / `h-11 w-11`
  с откатом `sm:` на десктопный размер): крестики диалогов и панелей, звёзды оценки, чипы
  фильтров, кнопки действий в карточке заказа.

## Строки таблиц: гибрид Firestore + Supabase (23.09.2026)

Строки столов — самая частая операция и главный расход квоты Spark — могут жить в **Supabase
Postgres** (`desk_rows`), где суточной квоты на операции нет. ВСЁ остальное (участники, столы,
вкладки, заказы, график, права) — в Firestore, как было. Где сейчас строки — `workspace.rowsBackend`
(`"supabase"` или нет поля = Firestore); переключает ТОЛЬКО Owner в «Настройки → Строки таблиц»
(`RowsStoragePanel`) вместе с переносом (`rowsMigrationService`: туда и обратно, сверка числа
строк в КАЖДОЙ таблице — не сошлось, хранилище не переключается; после переключения
`reloadEpoch + 1`). Пока идёт перенос, у workspace стоит `rowsMigrationAt`, и `assertRowsWritable`
запрещает правку строк во всех сессиях (флаг старше 15 минут считается мёртвым —
`ROWS_MIGRATION_STALE_MS`, кнопка «Снять флаг»).

- **Один переключатель на весь код.** `pageService`/`subPageService` (и вложения, бэкап, снимки
  стола, статистика «Столов ОС») сами смотрят `usesSupabaseRows(workspaceId)` и идут либо в
  Firestore, либо в `services/rows/supabaseRowStore.ts`. Остальной код не знает, где строки.
  Значение — модуль `services/rows/rowsBackend.ts`; в него его кладёт `useRowsBackendBridge`
  (первым хуком `AppLayout`, и ещё при ОТРИСОВКЕ через `primeRowsBackendState` — эффекты стола
  идут раньше эффектов `AppLayout`). `useSyncedTableRows` ждёт, пока хранилище известно, и
  переподписывается при смене. Старое зеркало `row_records` (Firestore + копия в Supabase
  анонимным ключом) УДАЛЕНО: оно читало стол дважды и квоты не экономило.
- **Вход — токеном Firebase.** Отдельный клиент `lib/supabaseRows.ts` (`accessToken` = ID-токен
  Firebase; Supabase → Third-party Auth → Firebase). Общий `lib/supabase.ts` (анонимный ключ)
  остался ТОЛЬКО для Storage — его политики написаны под роль anon.
- **Права — копия прав Firestore в Postgres** (`rows_workspaces` / `rows_members` /
  `rows_page_acl` / `rows_desk_observers`), политики `desk_rows` повторяют `canAccessPage`/
  `canEditPage`. Копию доводит до Firestore `useRowAclSync` (Owner — всё, Тимлид — что ему
  разрешено, ответственный — свой стол; чистые решения в `planMemberSync`/`planPageSync`).
  Политики на запись копии разрешают РОВНО то, что firestore.rules на те же поля, поэтому
  подменой копии нельзя получить больше, чем честной правкой в Firestore. Сверка НИКОГДА не
  удаляет записи столов (неполный список столов снял бы права у всех) и убирает участников
  только по свежему с сервера списку (`fetchMembersFresh`) и не больше трети разом.
  Убрали человека / выдали наблюдателя / удалили стол — копия правится СРАЗУ в том же действии.
  `rows_workspaces` клиент не пишет вообще: строку владельца Owner вставляет в SQL-редакторе
  (готовая строка на экране), иначе владельцем объявил бы себя первый пришедший.
- **Firestore-копия строк в режиме Supabase — замёрзший архив**: правила (`rowsWritableHere`)
  отклоняют запись строк ВСЕМ, и Owner тоже — пишет он только пока идёт откат (`rowsMigrating`). Громкий отказ вкладки на старом коде
  лучше тихой потери правки. `rowsBackend`/`rowsMigrationAt` Тимлиду не писать.
- **Права ещё не доехали** (новый стол, Owner/Тимлид не в сети) — политика отдаёт пустоту, как
  при пустом столе; `useSyncedTableRows` спрашивает `rows_page_access` и стол показывает
  плашку «строки пока не видны, не вбивайте заново».
- **Настройка у Nurba** (один раз): Third-party Auth → Firebase `nurba-6e70d`; SQL
  `supabase/migrations/20260923_desk_rows.sql` в SQL Editor (повторяемый); строка владельца.
  Кнопка «Проверить» (`rows_whoami`) говорит, какой шаг не сделан.
- **Живые строки (`sbSubscribeRows`) — уроки ревью.** Своя правка ложится ПОВЕРХ строк сразу
  (`optimistic` + `Overlay`): Firestore-SDK показывал её до ответа сервера, и `DataTable` своего
  оптимистичного слоя не имеет — без этого введённое значение откатывалось, пока не придёт
  Realtime. Подтверждённая правка снимается событием по её строкам, свежей выборкой или через
  5 с; отказ базы снимает её и перечитывает таблицу. События применяются в порядке ПРИХОДА, а
  не по `updated_at` (это `Date.now()` разных устройств — отстающие часы выбрасывали бы чужие
  правки); пришло во время выборки — выборка повторяется. Удаления слушаются ОТДЕЛЬНЫМ
  обработчиком без фильтра: фильтр по столбцу на DELETE в Supabase не действует. Канал не
  подключён — после своих правок таблица перечитывается (выборка не тарифицируется, а при
  живом канале полной выборки на каждую правку НЕТ: на 5 ГБ трафика в месяц этого не хватило
  бы). Ошибка выборки — `onData` не зовётся (иначе строки прошлой вкладки выглядели бы
  строками этой), повтор 3 → 30 с.
- **Пустота в Supabase — не «данные с сервера», пока право читать не подтверждено**
  (`useSyncedTableRows`): RLS отказ не называет, и стол без доехавших прав публиковал бы нули
  в «Технари» (`serverSynced` держится false). Пока висит плашка — `rows_page_access` раз в
  15 с; права доехали — таблица перечитывается сама.
- **Id нового стола — `page_{uidСоздателя}_…`** (`generateDeskId`): запись прав в Supabase
  создатель заводит сам, и политика пускает только стол со СВОИМ uid в id — иначе технарь,
  увидев id чужого нового стола раньше сверки, объявил бы себя ответственным. Старые столы
  заводит Owner при переносе.
- **Замок переноса держат правила Firestore** (`rowsMigrating`): `rowsMigrationAt` пишется
  `serverTimestamp()` (часы Owner не годятся) и запирает запись строк всем, кроме Owner, на
  15 минут. Клиентский `assertRowsWritable` — лишь быстрый отказ; вкладка на старом коде его не
  знает. Читать поле — `migrationStartMillis()` (Timestamp или старое число).
- **Замок с другой стороны — в Supabase** (`rows_workspaces.live`/`migrating_until`,
  `rows_set_state`, только Owner; писать в `desk_rows` можно лишь в `rows_writable_workspaces()`):
  до переноса и после отката хранилище НЕЖИВОЕ, и правка вкладки, не узнавшей о смене, падает
  громко, а не оседает в брошенном хранилище. Во время переноса туда пишет только Owner, не
  дольше 15 минут. Перенос сам ставит `false/true` → `true/false`, откат — `false/false`; сбой
  возвращает прежнее.
  Если workspace перенесли ДО появления замка, повторный накат SQL добавит `live = false` и
  запрёт строки всем — поэтому сессия Owner (`useRowAclSync` → `reconcileSupabaseLive`)
  открывает хранилище сама, когда в СВЕЖЕМ с сервера документе workspace `rowsBackend:
  "supabase"` и флага переноса нет (откат сначала пишет флаг, потом запирает Supabase).
- **Копия прав — по СВЕЖЕМУ чтению**: `useRowAclSync` сверяет участников и наблюдателей только
  по `fetchMembersFresh`/`fetchDeskObserverUidsFresh` (сервер, мимо кэша) — при загрузке и раз в
  30 минут; ростер вкладки через час врёт и вернул бы права убранному. Мгновенные изменения
  действие пишет в копию само: роль/вторая роль (`pushMemberToRowsAcl`), одобрение заявки,
  «убрать»/полное удаление (`dropFromRowsAcl`), наблюдатель, новый стол (`ensureNewDeskAcl` в
  `createPage`/квоте/столе ОС/`duplicatePage` — копия стола получает id и `createdBy` того, кто
  копирует, иначе своя запись прав не проходила политику).
- **Выборки строк** (`supabaseRowStore.ts`): первая страница спрашивает `count: exact`, и
  чтение идёт до этого числа — `max_rows` проекта могут поставить меньше 1000, и «короткая
  страница» перестала бы значить «всё». Пустая выборка в `sbFetchRows`/`sbFetchRowsSince`/
  `sbFetchAllPageRows` сверяется с `rows_page_access`: нет права — `permission-denied` (не
  участник или права не доехали — `unavailable`), как Firestore, а не «пустой стол» для бэкапа
  и копии вкладки. Подписка это не проверяет — там разбирается `useSyncedTableRows`, и после
  подтверждения прав перечитывает таблицу ещё раз (права могли доехать между выборкой и
  проверкой).
- **Realtime-событие правки НАКЛАДЫВАЕТСЯ на сохранённую запись** (`serverRecords`): большие
  jsonb (ячейки длинной строки, вложения) Postgres хранит в TOAST и в событие правки их не
  кладёт — замена стирала бы строке ячейки. Нет записи и не хватает полей — выборка. Чужие
  события (слушатель удалений без фильтра) отсекаются ДО флага «перечитать», перерисовка по
  событиям — одна на 16 мс, своя правка — синхронно.
- **Записи одной строки идут в базу ПО ОЧЕРЕДИ** (`sequenced`, ключ стол+вкладка+строка):
  каждая — отдельный HTTP-запрос, и два быстрых ввода в ячейку доходили наоборот. Разные строки
  — параллельно, запись всей таблицы (удаление, порядок) ждёт все до неё. Подтверждённая
  правка, по которой за 5 с не пришло событие, снимается выборкой, а не откатом экрана.
- **Перенос берёт только ВИДИМЫЕ строки**: подписка Firestore идёт с `orderBy("order")` и
  документы без `order` не показывает — их не переносим и при откате не удаляем. Даты старых
  документов бывают `Timestamp` или отсутствуют — `firestoreDocToRow` переводит в мс
  (`createdAt` ← `updatedAt` ← 0), иначе `rowToRecord` поставил бы «сейчас» и старые заказы
  попали бы в сегодняшние сводки.
- **Защита переноса (аудит 23.09.2026).** Список столов перенос читает СВЕЖИМ с сервера
  (`fetchPagesFresh`), а не из памяти вкладки: неполный список молча стал бы эталоном, и не
  попавшие в него столы открылись бы пустыми. Замок переноса продлевается, пока идёт
  копирование (`startMigrationLockKeeper`, раз в 4 минуты), а перед переключением проверяется
  (`assertFresh`, потолок 12 минут): замок живёт 15 минут, а большой перенос идёт дольше — он
  отпустил бы чужие вкладки, и их правки в старом хранилище пропали бы. Откат перед КАЖДЫМ
  удалением сверяет, что прочитал из Supabase всё (`supabaseCount`) и что пустой ответ —
  правда пустой стол, а не скрытые политикой строки (`sbPageAccess`): иначе он стёр бы живую
  копию Firestore, а сверка подтвердила бы «ноль = ноль».
- **Отказ, понятный человеку.** Правка во время переноса — «Идёт перенос строк таблиц»
  (`isRowsMigratingError`, код `rows-migrating` в `dbError.ts`), а не «Не удалось сохранить ·
  Повторить» по кругу; заезд заказа в этот момент не зовёт жать кнопку, которая тоже откажет.
  Строки не прочитались — у стола полоса с причиной и «Повторить сейчас»
  (`useSyncedTableRows().readError/retry`), а не вечный пустой скелет. Опрос прав
  (`rows_page_access`) идёт только в ВИДИМОЙ вкладке и сразу при возврате на неё.
  Запись прав в копию: `upsert` — это INSERT ON CONFLICT, и Postgres проверяет политику
  ВСТАВКИ даже при правке существующей записи, поэтому отказ `42501` повторяется обычным
  `update` (иначе ответственный за старый стол не мог обновить даже свою запись).
- **Живой канал и обрыв связи.** Канал не поднялся за 15 с — человеку один раз говорят
  «Живое обновление строк не работает: свои правки сохраняются, чужие появятся после
  обновления страницы» (молчащий канал выглядел как «коллега ничего не делает»). Запись при
  обрыве повторяется 1 → 3 → 7 с и ТОЛЬКО на код `unavailable` (`writeWithRetry` внутри
  очереди строки): у Supabase нет очереди офлайн-записей, как у Firestore-SDK, и каждая кочка
  в метро иначе давала бы «не удалось сохранить». Отказ прав или данных не повторяется.
  Таймеры зачистки и перечитывания не ставятся после ухода со стола (`cancelled`).
- **Вставка записи о столе в копию прав** (`rows_page_acl_insert`, 23.09.2026 после аудита):
  Тимлид заводит запись о столе ОС только ЧУЖОМУ человеку и не может выдать обычный стол под
  id `osdesk_…` — иначе он объявлял бы себя ответственным за чужой стол ОС (с `os_desk: false`)
  и, будучи ещё и Технарём, получал правку его строк, хотя в Firestore ответственного у стола
  ОС ему менять нельзя. Свой стол ОС Тимлид + ОС заводит веткой участника, где роль ОС
  проверяется. **Владельца по документу workspace без member-документа в наборах прав НЕТ
  намеренно**: правило строк в firestore.rules — `isMember && canAccessPage`, то есть и там он
  строк не читает; копия повторяет Firestore, а не даёт больше.
- **Проверено**: 123 проверки RLS на локальном Postgres 16 (`supabase/tests/desk_rows_rls.sql`
  поверх `supabase_stub.sql` — роли anon/authenticated и `auth.jwt()` как у Supabase); 30
  юнит-проверок планов сверки; 29 проверок правил Firestore эмулятором (включая замок
  переноса и Owner вне отката); 68 сквозных проверок НАСТОЯЩЕГО кода (перенос туда/обратно, самолечение замка,
  неживое хранилище до и после, документы без `order` и с `Timestamp`, порядок быстрых правок,
  сервисы строк, оптимистичная подписка без Realtime, откат отклонённой правки, отказ вместо
  «пустого стола» у чужих) —
  эмулятор Firestore + PostgREST 12 (бинарник с GitHub-релиза) над тем же Postgres, токены
  HS256 с теми же claims; хук стола в браузере — 5 проверок в режиме Firestore и 5 в режиме
  Supabase (нули без прав не публикуются, стол открывается сам, когда права доехали); 12
  проверок разбора событий на поддельном канале (частичное событие правки, чужие удаления,
  склейка перерисовок, очередь записей). Настоящий сервер Realtime локально не проверен.

## Стол ОС — источник заказов (23.09.2026)

Заказ ведёт ОС, а не технарь (просьба Nurba). Технарь свой стол руками больше не заполняет:
заказ приезжает к нему со стола ОС и с этой минуты ему НЕ принадлежит — статус, сумму, клиента
и ОС правит только ОС. Технарю оставлены две вещи: ссылка на сделанную работу и примечание,
плюс просьба «поставьте „Успешку“» — решают её ОС этого заказа, Тимлид или Owner.

- **Строка-заказ** — обычная строка в столе ТЕХНАРЯ с меткой `osUid` (+ `techUid`, `statusKey`,
  `srcPageId/srcTabId/srcRowId`, `syncHash`). Заказ не переезжает намеренно: по строкам стола
  технаря считаются `deskLoad`, «Технари», дашборд, оценки и загрузка — их за день читают
  десятки мест. У ОС лежит строка-ИСТОЧНИК (его стол) с адресом копии
  (`mirrorPageId/mirrorTabId/mirrorRowId`).
- **Замок держит БАЗА, а не интерфейс** (`supabase/migrations/20260923_desk_rows.sql`: политики
  `desk_rows` + триггер `desk_rows_guard`): технарь ответственный за свой стол, и любое правило
  «только в UI» он обошёл бы сам. Owner — всё; ОС — свои строки (`os_uid = uid`) в чужих столах;
  Тимлид — РОВНО ячейку `status_key` («Успешка» по просьбе); технарь — только `techLink`/
  `techNote` и свою просьбу об «Успешке»; опорные поля строки-заказа меняет один Owner.
  На клиенте то же читается `cellLockReason`/`rowDeleteLockReason` (`utils/managedRow.ts`) —
  редактор не открывается и строка не удаляется, с объяснением в тосте.
- **`techLink`/`techNote` — зарезервированные ключи ячеек** (`utils/reservedCellKeys.ts`):
  столбец с таким ключом завести нельзя (`addColumn`/`addSubPageColumn`/`AddColumnDialog`),
  иначе «технарю можно только эти два ключа» обошлось бы заведением своего столбца.
- **Куда писать в чужой стол — `page.osFieldKeys`** (`utils/osFieldKeys.ts`,
  `useOsFieldKeysPublisher`): подвкладки чужого стола ОС не прочитает, а документ стола читают
  все участники, поэтому стол САМ публикует карту своих столбцов текущей месячной вкладки
  (пишется только при смене набора столбцов). Ключи от другой вкладки = отказ выдать заказ
  («пусть откроет свой стол»), а не запись значений в чужие ключи.
- **Цена и апсейл у технаря складываются в ОДНУ сумму** (50 000 + 50 000 = 100 000, решение
  Nurba): у технаря один денежный столбец, по нему считаются загрузка, дашборд и рейтинг.
- **Статус ставится из КАРТОЧКИ строки** (`OsOrderPanel` в `RowCardSheet`), столбца статуса на
  столе ОС нет намеренно. Панель читает настоящий статус из строки технаря
  (`useMyOrderRows` — ОДИН запрос на весь стол ОС: политика отдаёт ровно строки с его `os_uid`,
  доступ к самим столам для этого не нужен), показывает «правка не доехала» по расхождению
  `syncHash` и чип «технарь просит „Успешку“».
- **«Выдать в работу» = «Обновить у технаря»** (`osOrderMirror.pushOrderToTech`): id копии
  выведен из id источника, повтор пишет в ту же строку. У ПЕРЕНЕСЁННЫХ заказов копия — исходная
  строка технаря, её id так не выводится, поэтому панель передаёт `mirrorRowId` явно (иначе
  рядом заводилась бы вторая строка того же заказа).
- **«Заказы заводит только ОС»** (`workspace.osManagedDesks`, переключатель Owner в «Настройки →
  Строки таблиц») — у технаря в его столе пропадают «Строка» и «Быстрый заказ». Стол ОС и Owner
  не ограничиваем. Сами строки-заказы технарь не правит в ЛЮБОМ случае — это держит база.
- **Разовый перенос старых заказов** (`services/rows/osOrderAdoption.ts`, кнопка у Owner):
  заказы ТЕКУЩЕГО месяца с ником ОС получают строку-источник в столе этого ОС (стола нет —
  заводим по нику) и замок. Не трогаем: пустые слоты, уже управляемые, строки без ника ОС и
  ники без живого аккаунта. Id источника выведен из строки технаря, поэтому повтор обновляет те
  же строки. Рядом аварийный выход «Снять управление» (`releaseAllOrders`, `p_release_order` в
  `rows_patch`) — по ВСЕМ вкладкам: заказ сентября в октябре лежит в прошлой вкладке.
- **Тот же замок продублирован в `firestore.rules`** — страховка на случай, если строки вернут
  в Firestore кнопкой отката: метка `osUid` на документе остаётся, и без этой ветки технарь
  снова правил бы статус и сумму своего заказа. ВЕСТИ заказы из Firestore всё равно нельзя —
  ОС не пишет в чужой стол (`canEditPage`), и это осознанная граница: режим Firestore здесь
  только для отката.
- **Проверено**: 156 проверок RLS на локальном Postgres 16 (`supabase/tests/desk_rows_rls.sql`),
  23 проверки правил Firestore эмулятором (`managed.mjs`: технарь, Тимлид, Owner, ОС, вкладка
  месяца, создание строки с чужой меткой) и 26 юнит-проверок переноса на заглушках; панели и
  замок — на стенде в браузере.

## Модель прав (кратко)

Roles: `owner` > `teamlead` («Тимлид») > `admin` > `manager` («Технарь») > `os` («ОС») / `viewer`. Owner и
Тимлид проходят `hasFullAccess()` безусловно (`isOwner()` — только Owner: удаление workspace). `canEditPage(page) = owner/тимлид || responsibleUserId == uid || (canAccessPage && uid in editableUsers)`.
`canAccessPage(page) = owner/тимлид || isResponsiblePage || uid in allowedUsers`. `allowedUsers`
(просмотр) и `editableUsers` (редактирование) — разные права. `responsibleUserId` даёт
админ-права в рамках конкретной страницы + доступ на чтение даже без `allowedUsers`, но не
доступ на уровне workspace. История изменений (`/history`) — Owner и Тимлид.

**«Режим доступа»** (симуляция роли, `activeRole`) — функция ТОЛЬКО Owner. У Тимлида и Admin её
забрали (`allowedSimulatedRoles` + ветка `activeRole` в правилах); застрявшая старая симуляция
снимается сама — клиент не доверяет `activeRole`, который текущая реальная роль не вправе
симулировать, а запись `null` правило разрешает всем.

**«Наблюдатели»** (скрытая страница `/observers`, `deskObserverService.ts`, коллекция
`deskObservers/{uid}`) — тихое право Owner: человек видит ЧУЖИЕ столы на ЧТЕНИЕ. Страницы нет
ни в меню, ни в поиске — только прямой адрес; не-Owner видит там пустую заглушку без единого
слова «наблюдатель». Признак лежит ОТДЕЛЬНОЙ коллекцией, а не полем в `members`:
member-документы читает весь workspace, и признак был бы виден каждому. Читают документ только
Owner (весь список) и сам наблюдатель (ровно свой) — поэтому ответственный за стол и не узнаёт,
что за ним смотрят; в `allowedUsers` наблюдатель не попадает, в «Доступе к столу» не значится,
запрос на просмотр не шлёт, уведомлений не создаёт. Следов не оставляет и потому, что
`useDeskLoadPublisher` требует `canEditPageData` — из чужой сессии счётчики не публикуются.
Права ровно на просмотр: `canEditPage` по-прежнему требует ответственного или `editableUsers`,
личная зона чужого стола закрыта (`canUsePersonalZone` не тронут). На клиенте право влито в
существующий `seesAllDesks` (тот же путь, что у Тимлид+Технарь), в правилах — в `canAccessPage`,
и в обоих местах проверяется ДО `isDeskBlocked`: право выдано человеку, а не роли, поэтому
работает и у Тимлида, и у ОС (им же показывается пункт «Столы»). Читается РАЗОВО при загрузке
(`useDeskObserverLoad`, без `onSnapshot`) и лежит на модуле — выдали при открытом приложении,
человек увидит столы после перезагрузки. Проверено эмулятором — 25 проверок (`observers.mjs`):
наблюдатель читает чужие строки и вкладки, но не пишет, не правит стол и не лезет в личную зону;
чужой технарь и Тимлид без права — отказ; список наблюдателей читает только Owner, сам
наблюдатель видит лишь свой документ, право себе не выдаёт и не снимает.
**Честная граница:** репозиторий ПУБЛИЧНЫЙ, так что «скрытая» здесь значит «не видно в
интерфейсе», а не «невозможно узнать о существовании функции». Скрыто именно то, что важно:
КТО наблюдатель. Ещё: комментарий к строке наблюдателю технически доступен (`canAccessPage`,
как у Тимлид+Технарь) — оставит след, если он сам его напишет.

**«Ключ доступа»** (`Настройки → Ключ доступа`, `ownerAccessService.ts`,
`ownerAccessRequests/{uid}`) — единственный путь выдать кому-то права Owner (в `RoleSelect`
роли Owner нет). Не-Owner видит на вкладке поле ключа `OWNER_ACCESS_KEY`; верный ключ только
ПИШЕТ заявку (id = uid, одна на человека) и шлёт уведомление всем Owner. У Owner та же вкладка
показывает СПИСОК заявок (перечитывается при каждом входе на вкладку — подписки там нет).
Кнопки «Выдать права»/«Отклонить» есть и там, и в колокольчике
(`NotificationBell`, `kind: "owner-request"`), выдача =
`changeMemberRole(..., "owner")` и её делает Owner, поэтому ключ в публичном репозитории — просто
замедлитель, а не секрет: границу держат правила (`ownerAccessRequests` + members). Роль пишем
ДО смены статуса заявки — как в `resolveDeskViewRequest`. Заявки Owner читает разово (без
`onSnapshot`) — колокольчик и так висит на каждом экране.

В «Настройках» **нет кнопки удаления workspace** — «Опасную зону» убрали по просьбе Nurba
(правило `allow delete` у workspace и `deleteWorkspace()` в сервисе остались, UI к ним нет).

## Критические уроки и подводные камни (НЕ повторять)

- **`e.key` vs `e.code`** — `e.key` зависит от раскладки клавиатуры (на русской раскладке
  физическая Z печатает «я»). Горячие клавиши (Ctrl+Z/C/V…) всегда через `e.code`
  (`"KeyZ"`, `"KeyC"`...), никогда через `e.key`.
- **`serverTimestamp()`** нельзя использовать на полях, которые форматируются/показываются
  пользователю (`createdAt`/`updatedAt` и т.п.) — persisted-значение становится Firestore
  `Timestamp`, а не `number`, и код, ожидающий число, тихо расходится с типом или крашится при
  рендере. Использовать `Date.now()`.
- Firestore `delete`-правила никогда не проверяют `request.resource.data` — поле не существует
  при удалении.
- Firestore list-запросы (`collection().where(...)`) требуют однородных прав на все документы
  результата — иначе весь запрос падает `permission-denied`, даже если доступ есть к части.
  Personal Space (`personalZones/{uid}/reports`) поэтому изолирован по uid отдельной коллекцией.
- **`collectionGroup()`-запросы требуют отдельного top-level правила `match /{path=**}/...`** —
  вложенное правило под конкретным путём НЕ авторизует collection-group запрос. Отсутствие
  такого правила для `members` держало `claimPendingInvites()` (auto-claim инвайта при логине)
  в вечном молчаливом `permission-denied` для абсолютно всех — если добавляешь новый
  `collectionGroup()`-запрос, сразу заводи парную `{path=**}`-rule.
- Экранный `hasOnly([...])`/`affectedKeys()` diff-чек в `firestore.rules` обязан включать
  **ровно** те поля, что реально пишет клиентская функция за одну операцию — не меньше и не
  больше. Несовпадение тихо роняет весь write с `permission-denied` для не-Owner, при этом
  кнопка в UI остаётся видимой и как будто рабочей. Уже наступали на это дважды (assign-
  responsible писал `allowedUsers`+`hiddenByResponsible` вместе с `responsibleUserId`;
  `changeColumnType` ронял `statusOptions`) — при правке ЛЮБОГО `hasOnly`-правила или функции,
  которая под него попадает, перепроверяй оба конца.
- **В языке Firestore rules нет `list.filter()`/`list.all()`/лямбд.** Был
  `columnStatusOptionsPreserved()` на них: файл «компилировался» (только warnings), а в рантайме
  функция падала, и Технари месяцами не могли сохранить столбцы, переименовать стол, скрыть его
  и т.п. — молча. Удалён; ответственный правит свой стол целиком, кроме
  `responsibleUserId`/`createdBy`/`workspaceId`, редактор — вкладки, кроме их идентичности.
  Правила проверяй через `firebase deploy --only firestore:rules --dry-run`: warnings должно
  быть ноль, «compiled successfully» не значит, что правило работает. Ещё лучше — прогнать
  правила эмулятором: `npx firebase-tools emulators:exec --only firestore --project <любой>
  "node <скрипт>"` + `@firebase/rules-unit-testing` (java в облачной сессии есть). Так
  проверяются именно ПОЛОЖИТЕЛЬНЫЕ пути: молча ломается всегда то, что обязано было
  разрешиться. «evaluation error» в логе на пути, который и так обязан запретить, — обычный
  шум (Firestore считает оба правила, create и update, и лишнее падает на `resource.data`).
- **`resource.data.get('поле', дефолт)` в правиле ЧТЕНИЯ не ограничивает list-запрос.** На
  `grokAppAccounts` правило `resource.data.get('restricted', false) == false || uid in
  resource.data.get('allowedUids', [])` выглядело рабочим: точечный `get` закрытого документа
  отклонялся. Но запрос всей коллекции технарём ПРОХОДИЛ и возвращал закрытый аккаунт вместе с
  паролем — проверено эмулятором на голом примере: с `.get()` список отдаётся целиком, с прямым
  `resource.data.restricted == false` — отклоняется, как и должен. Правило чтения пиши прямым
  обращением к полю; плата — документ обязан это поле иметь, старым записям его проставляет
  разовый backfill. Проверять такие правила ТОЛЬКО точечным `getDoc` недостаточно: обязательно
  гоняй и `getDocs` всей коллекции от лица того, кому не положено.
- **Пустая карта в `setDoc(..., { merge: true })` СТИРАЕТ поле целиком.** SDK кладёт пустой
  объект в маску обновления как есть («создать пустую карту»), и сервер заменяет всё поле на
  `{}` — merge тут не спасает. Так `saveScheduleDraft` слал `hours: {}` при сохранении одних
  выходных и стирал человеку ВСЕ часы смен за месяц (а при сохранении одних часов — все
  выходные, «отпросился» и «пришёл»). Правила такую запись пропускают: набор ключей тот же.
  Карту в запись клади, только если в ней есть ключи; `deleteField()` внутри карты — это уже
  лист, он безопасен.
- **Не создавай новый объект в setState из ResizeObserver/scroll без сравнения** и не давай
  `?? []` в зависимости useMemo — в `DataTable` это давало бесконечный цикл «Maximum update
  depth exceeded»: страница тормозила, клики и перетаскивания терялись.
- Квоты на количество страниц у менеджера — только atomic Firestore batch writes, не
  читай-потом-пиши (race condition).
- **`activeRole`** (симуляция роли) — чисто клиентское UI-поле, Firestore rules никогда не
  должны ему доверять для реальных решений о доступе.
- «Статус», «Ответственный» и кастомные поля — не идентичны по модели resolution (детали в
  скилле `nova-crm-deep-dive`) — не переноси логику с одного типа на все три без проверки.
- Undo/redo — **глобальный** стек (`src/utils/undoStore.ts`), переживает навигацию между
  страницами, один слушатель Ctrl+Z на уровне приложения (`GlobalUndoHotkeys.tsx`) — не
  дублировать в `DataTable.tsx`. Многоячеечная операция (paste/clear/fill) обязана класть
  **ОДНУ** undo-команду на всю операцию (batch + `Promise.all`), не одну на ячейку — иначе один
  Ctrl+Z отменяет только последнюю тронутую ячейку.
- **Уже чинили дважды**: `column.type === "status"` для решения «можно ли редактировать текстом
  эту ячейку» — неполно. Нужно `isOptionColumn(column.type)` (status + responsible + custom),
  иначе двойной клик по «Ответственный»/кастомному полю включает фантомное текстовое
  редактирование, блокирующее ВСЕ горячие клавиши до перезагрузки.
- **Отказ в чтении (`permission-denied`) нельзя отдавать в success-колбэк как факт.** Так было в
  `subscribeToOwnMember`: денай маппился в `onData(null)`, `useWorkspace` помечал участников как
  подтверждённо загруженных, `findOwnMembership` ничего не находил и роль падала в `viewer` —
  полноправный Технарь везде видел «нет доступа»/только просмотр, а весь механизм `isResolved`
  (сделанный ровно чтобы не рисовать отказ поверх незагруженных данных) обходился, потому что
  этот путь сам заявлял «загружено». Owner баг не воспроизводил: у него шорткат
  `isOwnerOfWorkspace` от документа workspace, а не от member-документа. Отказ = «не
  подтверждено», а не «данных нет». И помни: `onSnapshot` после ошибки НЕ переподключается сам —
  без явного ретрая такое состояние терминальное до перезагрузки страницы.
- Любое действие в UI, которое пишет НЕ в тот документ, что остальные соседние действия, должно
  иметь свой отдельный гейт. Примеры, на которых уже обожглись: ширина/порядок столбцов на
  «Основной» пишутся в сам `pages/{pageId}` (только Owner/ответственный), а внутри вкладки — в
  `subpages/{id}` (можно любому редактору); «сделать вкладку открываемой по умолчанию» пишет
  `defaultSubPageId` в документ страницы, хотя стоит рядом с обычными действиями над вкладками.
  Гейт по «праву на данные» (`canEditPageData`) там, где нужен структурный
  (`canManagePage`), даёт молчаливый откат: запись отклоняется, тост не показывается, значение
  возвращается на место.
- Подписка на Firestore-коллекцию (сообщения/переписки и т.п.) вначале отдаёт пустой массив (до
  первого снапшота), потом реальные данные — паттерн должен быть «видел ли я именно ЭТО», а не
  «это первый вызов эффекта». Также: React-компонент, который переиспользуется между разными
  «логическими» инстансами БЕЗ ремонта (тот же route, сменился id/prop) — обязан явно очищать
  свой стейт вверху эффекта при смене id, а не только когда id стал falsy.
- **Экран загрузки не должен висеть молча.** Если `users/{uid}` не прочитался (нет сети,
  расширение-«ускоритель» рвёт соединение Firestore, отказ), `profileResolved` ставится, а
  профиль пуст — фаза навсегда «profile». Ошибку теперь несёт `bootstrapStore.bootError`, и
  `AppBootScreen` показывает её прямо на экране с «Обновить страницу»/«Выйти»; на любой
  стадии дольше 12 с — подсказка про сеть и расширения. Раньше единственным сигналом был
  тост, и его у Nurba закрыло уведомление расширения SuperchargeBrowser в том же углу.
  Кнопка на этом экране — «Обновить в режиме совместимости»: она ставит в localStorage
  `nova:firestore-long-polling=1`, и `firebase.ts` на этом устройстве создаёт Firestore с
  `experimentalForceLongPolling` вместо автоопределения. Нужна для расширений-«ускорителей»,
  антивирусов и прокси, которые КОПЯТ потоковый ответ базы: соединение формально открыто,
  документов нет, `getDoc` висит без ошибки (обычный обрыв сети дал бы «client is offline»
  за ~10 с). Две настройки взаимоисключающие — передавать ровно одну, иначе SDK бросает.
  **Реальная причина вечной загрузки 22.09.2026 была другой — сбой узла Google.** Весь кластер,
  куда Казахтелеком и DNS Cloudflare резолвят `firestore.googleapis.com` (74.125.205.x,
  64.233.164.x, 108.177.14.x), открывал сессию WebChannel (POST → 200 и SID), а обратный канал
  отвечал `400 Unknown SID` — даже в том же TCP-соединении. В консоли это «Failed to load
  resource: 400» на `firestore.googleapis.com` и «WebChannelConnection RPC 'Listen' stream …
  transport errored». Режим совместимости тут не помогает (long polling — тот же протокол с
  SID). База и квота были целы: через узел из DNS Google (8.8.8.8 → 142.251.20.95) тот же
  запрос отдавал нормальный Listen. Диагностика без входа: curl POST на
  `/google.firestore.v1.Firestore/Listen/channel?database=…&VER=8&RID=1&CVER=22&X-HTTP-Session-Id=gsessionid`
  с `count=0`, затем GET с `gsessionid`/`SID`/`RID=rpc`/`TYPE=xmlhttp`, и то же с `curl --resolve
  firestore.googleapis.com:443:<ip>` на другие узлы. «Проверил в своём браузере — тоже висит,
  значит глобально» — ложный вывод: браузер Claude работает с той же машины и сети, что и
  владелец. Из кода узел не выбрать (`firestore.clients6.google.com` и
  `content-firestore.googleapis.com` резолвятся в тот же сломанный кластер), поэтому экран
  загрузки теперь показывает рецепт: безопасный DNS Google в Chrome, «Частный DNS dns.google» на
  Android, 8.8.8.8 на iPhone по Wi‑Fi, или VPN.
- **iOS Safari / Google OAuth**: `authDomain` должен быть `firebaseapp.com`, не `web.app`
  (иначе `redirect_uri_mismatch` на iPhone). Мобильный Google-логин — `signInWithRedirect`, не
  `signInWithPopup`. `getRedirectResult()` не должен блокировать/ложно фейлить обычный
  email+password вход дольше пары секунд (даже если есть флаг «редирект ожидается» — он может
  быть устаревшим), и не должен реагировать на преждевременный `null` от Auth.
- **Чат — только последние сообщения.** Счётчик непрочитанных в меню (у ВСЕХ, `useInboxSummary`
  из `Sidebar`) был подписан на ВЕСЬ общий чат за всё время, и меню переподписывалось при
  каждом переключении полноэкранной таблицы и открытии меню на телефоне — тысячи чтений на
  каждого человека в день. Теперь `subscribeToRecentChat` (`orderBy serverOrderAt desc` +
  `limit`): счётчику хватает 10 последних (`UNREAD_WINDOW`), страницам чата — 300, вся история — только по
  «Показать ранние сообщения». Подписки меню общие на приложение и живут минуту после ухода
  последнего читателя (`joinSharedSubscription`) — повторный монтаж меню ничего не читает.
- **Не перечитывать список участников по таймеру.** «Пользователи» и «Команда» читали весь
  `members` (~40 документов) КАЖДУЮ минуту, пока открыты — до 2 400 чтений в час на вкладку.
  Теперь `useMembersRefresh`: при открытии экрана и возврате на вкладку, не чаще раза в 5 минут.
- **Квота Spark — что уже экономит пакет 22.09.2026 и чего не ломать** (аудит насчитал ~230k
  чтений и ~19k записей в сутки при лимите 50k/20k):
  - **LRU-кэш Firestore в памяти** (`firebase.ts`: `memoryLocalCache` + `memoryLruGarbageCollector`,
    40 МБ) — повторная подписка и повторный запрос берут документы из кэша и платят только за
    изменения. Цена: повторная подписка СНАЧАЛА отдаёт снимок из кэша, сколько угодно старый.
    Рисовать по нему можно, РЕШАТЬ нельзя: публикация счётчиков стола ждёт снимка с сервера
    (`subscribeWithSource` в `firebase/firestore.ts` → `useSyncedTableRows().serverSynced` →
    `useDeskLoadPublisher({ rowsFromServer })`), автозаезд заказа пропускает `fromCache` и
    сверяет заказ с сервером, `subscribeDeskLoads` отдаёт `fromCache`, пересчёт Owner ждёт
    `synced`, вкладки стола ждут сервер до 1,2 с. Новый код, который ПИШЕТ по результату
    подписки, обязан так же смотреть `metadata.fromCache` (с `includeMetadataChanges`, иначе
    переход «кэш → сервер» без изменений документов не придёт). Выход из аккаунта перезагружает
    страницу — кэш прошлого человека не должен кормить подписки следующего.
  - **Присутствие** — отметка раз в 15 минут (`usePresenceHeartbeat`, общая на вкладки браузера),
    «в сети» < 30 мин, «отошёл» < 90 мин; своё `lastActiveAt` не перерисовывает список участников.
  - **Счётчики столов** (`useDeskLoadPublisher`): пауза 10 с, при уходе со стола и сворачивании
    вкладки дописывается сразу; память «уже записано» в localStorage (`hash@время`) верится 90
    минут и только первому расчёту после открытия; пересчёт Owner — только столов старше 2 часов
    или с другой вкладкой, проверка раз в 15 минут.
  - **Leaderboard** — пишется только полный, свежий (прочитанный с сервера в этот заход) и
    изменившийся; память записи — 90 минут. Свои столы дашборд читает мимо 15-минутного кэша.
  - **Уведомления** — живое окно 40 последних (индекс targetUid + createdAt desc; пока индекс
    строится — откат на полный запрос), «прочитать всё» и открытие переписки добирают
    непрочитанные ЗА окном отдельным узким запросом; раз в сутки удаляются свои прочитанные
    старше 14 дней.
  - **Заказы** — живая подписка только на `open`/`assigned`, история («В столах»/«Отменённые»)
    постранично (`startAfter`) и счётчиками `getCountFromServer`.
  - **Ячейки** — вставка/заполнение пишут одну запись на строку, а не на ячейку.
- **Firebase Spark listener limits**: не вешай новые постоянные `onSnapshot` бездумно на
  второстепенные экраны — упрёшься в лимиты бесплатного плана. Строки таблиц — см. «гибрид»
  выше (`supabaseRowStore.ts`).
- **Postgres RLS — уроки гибрида.** (1) Проверка прав функцией «на строку» (`can_access(ws,
  page)` в политике) шла ~5 с на 3000 строк: SECURITY DEFINER-функции не встраиваются и
  считаются на каждой строке. Политика должна сверять строку с НАБОРОМ, посчитанным функцией
  без аргументов-столбцов (`(ws, page) in (select … from rows_readable_pages())`) — Postgres
  считает его один раз на запрос: стало 5 мс. (2) UPDATE/DELETE видит только строки, прошедшие
  политику ЧТЕНИЯ: без неё правка молча находит ноль строк (Admin «не мог» сменить
  ответственного). (3) PostgREST/Supabase отдаёт не больше 1000 строк за запрос — длинную
  таблицу читать страницами (`range`), иначе она молча обрезается. (4) Слияние ячеек — внутри
  базы (`cells || patch` в `rows_patch`), а не «прочитал-склеил-записал» в браузере: старое
  зеркало так теряло одну из двух быстрых правок одной строки.
- Отдельный standalone-проект «Living Archive CRM» архитектурно несовместим с Nova CRM, не
  пытаться сливать.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
